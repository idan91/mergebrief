# apps/api — agent notes

The Hono HTTP surface for the self-host backend. Its **webhook trust boundary** — `POST /api/webhooks/github` — verifies the HMAC over the raw body and parses the event through `github`'s Zod boundary. The event then maps, transactionally, to `persistence`'s tenant-scoped writes plus one debounced graphile `generate` job (`createIngestRoutines`).

This app owns its own process: `src/main.ts` is the startup wiring (`pnpm start`, the compose `api` service), the one place env is read and a real database is constructed, and it serves the top-level `/healthz` and `/readyz` ahead of the `/api` mount. `apps/web` proxies `/api/*` here and holds no credentials. `src/migrate.ts` is the second entry (`pnpm migrate`, `docker compose run --rm api migrate`): it reads `apps/api/.env` then the repo-root `.env` (never overwriting a shell value), loads only the database and `SERVER_VERSION` through `src/boot/`, then `runMigrate` applies the app schema with auto-migrate forced on and the queue schema, and exits 1 on any config error. Boot's check-only refusal names that command when `MERGEBRIEF_RUNTIME` marks the image, the checkout command otherwise.

Deliberately NOT here: page rendering, and any worker/LLM code. The api imports `brief-core` and `generators` only through their leaf subpaths, never an entry, so the process loads no adapter, dev CLI or provider SDK.

Repo-wide conventions apply (root AGENTS.md); refinements below.

## Invariants (enforced, don't weaken)

- **Verify before parse.** The HMAC is checked against the RAW request body (the exact bytes GitHub signed) before `JSON.parse`, before Zod, before any DB touch. Invalid/missing signature → 401 and NOTHING is written.
- **Tenant from the signed payload.** `TenantContext` derives from the payload's `installation.id` (branded by `github`'s parser, revalidated via `parseTenantContext`) — never from a spoofable header. All writes go through persistence's ctx-bound interfaces (`createTenantRepository`, `createIngestRoutines`, `createPurgeRoutines`); this package never sees a raw DB handle.
- **Fast 200, no compute.** The webhook handler only upserts rows and enqueues one job — no LLM calls, no GitHub API calls, no generation. Handled and ignored events alike return 200 quickly.
- **Idempotency is inherent, not bolted on.** Natural-key upserts + `job_key = generate:{pull_request_id}` with replace semantics make redelivery safe; do not add dedup state here.
- **Deps are injected.** `createApp({ handle, webhookSecret })` — nothing in this package reads `process.env` or constructs a database; composition roots do.
- **The update check is anonymous.** `src/update-check` fetches the release manifest with a bare GET and the runtime's default User-Agent, nothing about the instance in the request; a `dev` or `0.0.0` `SERVER_VERSION` and `MERGEBRIEF_UPDATE_CHECK=false` never fetch. Composition injects `fetch`; the module never reads env.
- **Errors:** expected failures throw `ApiError` subclasses (sanitized 401/400 bodies via `onError`); persistence's `ScopeViolationError` renders there as the plain 404 a `NotFound` would, same body, code and audit reason; unexpected throws map to a sanitized 500 (internals go to the log, never the response). No secrets/tokens in messages or responses. The OAuth callback is the exception: a browser navigation, so every failure redirects home with `SIGN_IN_FAILURE_PARAM` instead of an error body, and a cancel on GitHub redirects to plain `/`.

## Wire error contract (enforced, don't weaken)

Every expected failure exits as a THROW of an `ApiError` subclass (`src/shared-errors/`): abstract `ApiError(code)` + exactly one class per HTTP status a wire code carries (`BadRequest`, `Unauthorized`, `Forbidden`, `NotFound`, `Conflict`, `PayloadTooLarge`, `TooManyRequests`, `InternalError`, `BadGateway`). `CodeFor<status>` constrains each class to codes of its status, so class/status/code cannot disagree. `app.onError` is the ONE producer of `{ error, code }` bodies, the 1:1 code→status map, the i18n line, and the uniform `no-store` posture (`errorJson` survives only inside it). Never hand-roll `c.json({ error })`, never call `errorJson` from a route or middleware. Non-`ApiError` throws render as sanitized 500s.

Layering: controllers are Hono-free and return `Result<T, XxxFailure>` for anything the handler must judge. They THROW only terminal, posture-free failures — never `Forbidden`/`NotFound` for a GitHub denial (that bypasses the uniform-404 collapse). Handlers own posture and the failure→throw mapping, which lives in the domain's `logic/wire-failures.ts` (a single trivial switch may stay inline). A GitHub failure becomes its `ApiError` through ONE mapper, `resolveGitHubDenialError(failure, posture)` (`shared-errors/github-denial`): `wire-failures.ts` answers its domain's own codes first (diff-too-large, file-absent, anchor-rejected, and kin) and hands the rest over with the call's posture. `collapse` is a read on the viewer's credential (403 → 404), `honest` a viewer write whose 403 is an FE-actionable capability signal (403 `github-permission`), `app-read` and `app-write` the same two on the installation credential, where a 401 is the instance's and answers 502. On the viewer's credential a 401 answers 401, refreshed or not; an outage or rate limit is 502 everywhere, never 404. Shared failure members wrap lower-layer errors whole (`github-denied { phase, error }`, `session-rejected { error }`) — no translating at the boundary. `Failure` = Result-side, `Error` = thrown (root `CONTEXT.md` glossary).

**Adding a new error code** (the recipe):

1. Add the kebab-case code to `ApiErrorCodes` in `packages/contract/src/errors.ts`, its status to `ApiErrorStatusByCode` (1:1 — a code needing two statuses is two codes), and its English line to `ApiErrorEnglishByCode`. A wire error carries no params: a code that would need one is two codes, or a sentence a translator writes without data. The status places the code in its class's `CodeFor<status>` automatically — throw it via that class.
2. Add the identical line as `errors.<code>` in `packages/i18n/src/locales/en.json` — `packages/contract/test/wire-pin.test.ts` pins completeness and wording equality against the exported maps.
3. Add the matching `pulls.briefError.<code>` copy in the catalog. `apps/web` needs no code mirror: it spreads `contract`'s map and adds only its own `malformed`. The copy lookup is total by a template-literal key type, so a missing entry breaks `apps/web`'s typecheck. The two catalog blocks are different copy: `errors.<code>` is the wire line, `pulls.briefError.<code>` is what a reader sees.

Security collapses stay at the per-domain handlers, BEFORE the wire: internal vocabularies (`GitHubApiErrorCodes` through the mapper, `RefreshErrorCodes`) map to thrown classes there. That keeps the uniform-404 posture. A wire code is already the public posture, never the internal cause.

## Domain layout (enforced, don't weaken)

The unit is the operation module, per the amended api-layering record under `docs/adr/`: it takes the database handle or a narrow deps slice, the resolved access value and the parsed input, returns a `Result`, and sits behind a thin HTTP adapter. A domain converts with its own change, and its pass-through controller goes then. `repos/pr/archive`, `delete` and `ready` set the converted shape:

- `index.ts` — the route factory: each declaration with its adapter, the only file that touches Hono. An adapter reads `pullRequestAccess` (or `repoAccess`), parses any input (`schemas.ts`), calls the operation, throws a failure through `logic/wire-failures.ts`, stamps the audit target and answers `c.json(..., NO_STORE)`, or `c.body(null, HttpStatuses.NO_CONTENT, NO_STORE)` when the success tells the caller nothing new.
- `<operation>.ts`, named for the operation (`mark-ready.ts`, `delete-pull.ts`): `(handle or a narrow deps slice, access, input?) → Promise<Result<T, XxxFailure>>`. It reads `access.row` and `access.rowScope` and never re-reads the row; GitHub goes only through `access.github`; writes go through `createTenantRepository(handle, access.rowScope)`.
- `types.ts` — the failure union. A GitHub refusal rides whole: `github-denied { phase, error: GitHubCallFailure }`.
- `logic/wire-failures.ts` — failure to `ApiError`. A mutation's fresh re-resolve (`fetchFreshRepository`, `repos/logic/fresh-repository.ts`) answers through `resolveFreshRepositoryError(error, access.footing)`; every other GitHub failure goes to the mapper with its posture.
- The binding: the repo gate binds `access.github` (`ReviewerGitHub`) over the request's one `SessionCredential` (`access/session-credential.ts`) before its own repo read, and that read, the installation walk and the route all ride it. Binding decrypts and calls nothing; a 401 renews once per request across every binding; an unreadable token deletes the session and answers 401. Behind an operator pass the per-PR step rebinds with `operatorReads`: the granted PR, its known commits loaded only when a denied read at commits asks. A session-only route (`generate`, `inbox`, the repo list) has no access value: its adapter binds `bindRequestGitHub(deps, session, log)` and hands that `RequestGitHub` to the operation and to the shared installation resolvers. Wire suites swap in the `github/testing` fake through `AuthDeps.bindReviewerGitHub` (`test/reviewer-github.ts`).
- The App's binding: an App-credential call binds `bindRepoInstallationGitHub(deps, access)` (`access/installation-binding.ts`) over the injected `AppDeps.bindInstallationGitHub`, only for a repo resolved into an Installation; minting waits for the first call. Wire suites pass the fake's (`buildFakeInstallationDeps`).

Until a domain converts, and wherever it still earns the pair, the handler and controller roles below hold. Every catalog domain is a folder with a closed role set at root:

- `index.ts` — the `xxxRoute` factory; composition only.
- `handler.ts` exports a named `createXxxHandlers(deps)` factory returning the domain's handlers object. Members parse and validate (Zod), call the controller, judge posture, and throw `ApiError` subclasses; success is a plain `c.json(...)`. The handler derives the tenant and passes `tenant: TenantRepository` down. A handler never calls the controller inside the response expression; the result lands in a named const first.
- `controller.ts` exports a single named `xxxController` object; op functions module-private, verb-first, 1:1 with handlers. Hono-free.
- `schemas.ts` / `utils.ts` (generic only) / `consts.ts` / `types.ts` (incl. the domain's `XxxControllerDeps` — narrow slices, never `AppDeps`; `log: Logger` rides deps).
- `logic/` — domain business logic; never at root, never in `utils.ts`.

A handler or controller body is orchestration only (~40 lines); computed logic extracts to a named, unit-testable function in `logic/`. Sibling routes sharing a path segment mount under one prefix in one routes file.

`routes/local-briefs` is dev-only: it serves `MERGEBRIEF_OUT_DIR`, which `loadConfig` drops in the shipped image (`MERGEBRIEF_RUNTIME`) or under `NODE_ENV=production`; with no dir its paths answer as unmounted, while its queries stay in the catalog.

No per-domain repository files — persistence's tenant-scoped stores are called directly. Every user-token GitHub call rides a binding from `AuthDeps.bindReviewerGitHub` or `AuthDeps.bindOperatorGitHub`; `main.ts` injects `github`'s, `buildAuthDeps` binds them over the throttle-off test octokit, and a fake suite passes the `github/testing` fake's. Nothing under `src/` constructs an octokit or mocks `github`; hand-rolled refresh locals and attempt counters are banned.

Tests: full-URL wire suites stay in `test/` (the byte-identity proof); unit tests colocate (`controller.test.ts`, `logic/x.test.ts`). The tell is whether the file imports `app.request`.

## Gated-route rules (enforced, don't weaken)

- **One gate per request.** The repos router (`routes/repos/index.ts`) mounts ONE method-agnostic gate (`src/access/`) over `/:repoId/*`, so the per-PR subtree, the collaborators leaf and the attachments purge share one positive cache, and the repo list at `/` never meets it. A new route under a repo inherits the gate and never mounts its own (a second gate double-checks access cold and can 404 a just-verified request). The gate sets `repoAccess` (reviewer, repo, footing, push bit, the repo's Installation, the operator pass's PR). The operator rung reads the PR from the path segment after `pulls`, so on the repo-level routes it never opens. The submit and collaborators tests pin single-gate behavior (the gate's repository reads). Behind it the per-PR subtree mounts one access step (`access/pull-request.ts`): a malformed `:prNumber` is the gate's 404, and a `requiresStoredPullRequest` operation gets `pullRequestAccess` (the repo access plus `prNumber`, `rowScope` and the row, a request-start snapshot).
- **The gate names the repo's world.** No credential holds a current installation. After the viewer's token proves read access, `repoAuthzLayer` asks the shared installation resolver (`routes/installation-resolver.ts`) which reachable installation holds the repo; `repoAccess.installation` becomes that installation for the rest of the request. In none, the repo is in no Installation and only its **URL** rows count, so a `requiresInstallation` operation 404s and the row resolution goes straight to the url-box row. Public and private repos alike, cookie and Bearer alike. The resolver's 401 and 502 are the gate's, never cached; a positive entry carries the resolved world and is keyed per credential and repo. The PAT rung below never asks and sets the owner world; `repoAccess.footing` is what steers it, so a per-PR route reading the world without the footing must not exist. The delete route (`repos/pr/delete`) sets `requiresInstallation`: the repository is re-read fresh with the viewer's token and the row deleted only on `permissions.admin` from THAT answer, never the walk's cached bit, and the viewer's shadowed url row at the same coordinates goes with it. The viewer's own pasted row is the inbox domain's session-only purge (`delete-own-pull`): no GitHub call, owner scope is the wall, so a pasted row in a repository nobody can read any more still goes, and both routes share `routes/purge-row.ts`.
- **The gate's second rung is the operator PAT, and it is narrow.** Url-box briefs generate behind a two-key ladder (reviewer token, then `MERGEBRIEF_URL_BOX_TOKEN`); the gate runs the same ladder. It retries ONLY when all five hold: the denial is 404/403, a PAT is configured, the reader owns the PAT (its numeric id equals the id GitHub's `GET /user` answered for the token at boot), the path names a PR, and that PR exists in the READER'S OWN url-box world.
  - `resolveOperatorTokenFor` (`access/operator-token.ts`) is the only reader of `deps.operatorToken`: the gate rung, the binding's `operatorReads`, the paste door and `bindOperatorReader` (the live read's operator reader) all take the token from it. Anyone else gets `undefined`, as does everyone while the owner lookup is pending or after GitHub refused the token: the same answer as an instance with no PAT, so no response may tell them apart. `main.ts` awaits the first lookup (`resolveOperatorTokenOwner`) before it serves.
  - A PAT-carried pass sets `viewerCanPush` false and `footing: operator`; the row resolution then reads only the reader's own url-box rows (the tenant-first probe would hand them the installation's rows).
  - The positive cache carries that footing AND the granted PR. The key is per-repo, so without the PR one pass would clear the gate for every PR in the repo.
  - A converted read reaches the rung through the per-PR binding's `operatorReads` (the owner-world conversation, the span diff, the file range); the row-less attachment read binds `bindGrantedPullRequestGitHub`, the same reach with no known commit. The rung is READS ONLY: every write runs on the viewer's token alone, so GitHub never attributes the operator for a reader's action. The attachment bytes fetch stays outside the bindings: a signed asset URL with no credential, a branch file on the viewer's credential only, never the operator's. One read chooses the operator itself: the live read (`routes/live-read`), whose denials are per alias inside a page that succeeded, which no binding fallback can see. It reads on the viewer's binding and asks an explicit operator reader (`bindOperatorReader`) only for the aliases GitHub showed nothing for or withheld: on PR meta only behind an operator pass, on the Inbox for the owner's own rows. A row withheld from the viewer is never marked unreachable on the operator's word alone. PR meta serves the row the read's own write returned, never the access step's snapshot.
  - A read that sends a caller-chosen ref to GitHub (the span diff, the file range) takes the rung only when every ref is a full SHA in `collectKnownCommits` (`access/known-commits.ts`): the row's base and head, each Brief span, each Delta span. Any other ref reads on the reader's token alone. The binding's `operatorReads` holds this; a route never re-checks it. The file `path` is NOT bound: any path at a known commit is readable.
  - The stack read never takes the rung: the open-PR list names every PR in the repository. A request the gate passed on the PAT gets `{ stack: null }` and no GitHub call.
- **Mutations re-resolve the repo fresh.** The gate's cached `repoFullName` is ≤60s stale — fine for reads; a rename + name-reuse inside the window would send a write to the wrong repo. A mutating route fetches `GET /repositories/{id}` with the viewer token immediately before the write. The re-resolve itself answers under the mapper's `collapse` posture (no existence leak); a request the gate passed on the PAT answers its 403/404 as 403 `no-repo-write-access` first. After a successful re-resolve the write's posture is a per-route judgment: `honest` where a FORBIDDEN carries an FE-actionable capability signal (mark-ready, thread resolution, submit, post-now), `collapse` where it carries none (the reply POST). The attachments branch write rides the App's credential under `app-write`: its 401 answers 502, and a rule refusing it answers 403 `attachments-disabled` first. NOT_FOUND collapses to 404 under every posture.
- **Policy is checked at the router seam, not in routes.** Every declaration states `browserSessionOnly`, `requiresPushAccess`, `requiresInstallation` and `requiresStoredPullRequest` (each field's doc in `product-operations/types.ts` says why it exists); `productRouter` composes one policy gate (`product-operations/policy-gate.ts`) in front of every operation's handlers, so a route added later is enforced automatically. The first failure answers, in this order: 401 no session, 403 cross-origin, 404 repo gate (malformed repo id or PR number, no access), 403 `scope-exceeded`, 403 `human-only` (a Bearer token on `browserSessionOnly`), 404 no push access, 404 a repo in no Installation, 404 no stored pull request, 400 parse, the operation. The ladder `read < private-write < external-write` is cumulative (queries need no scope check); no principal where one is needed fails closed with 401. Cookie principals are unlimited by construction; a Bearer principal carries `api_token.scope`, chosen at mint and immutable. The row loads through the per-PR step's `loadOperationRow` after the other checks; a `requiresStoredPullRequest` operation mounted without one throws.
- **The per-PR row world is resolved, not assumed** (`resolvePullRequestRow`, `access/pull-request.ts`). The repo's Installation is tried first; the url-box fallback is INSTANCE-wide, with a deterministic owner pick (own row first, else the oldest). Per-reviewer state is unaffected — the Review Session's natural key carries the reviewer. The delete route purges the row its access step loaded only when that row lives in the repo's Installation (a url fallback is its 404); the personal list and the inbox's own-row purge stay owner-bound and never use it.
- **`MergeBrief-Version` rides every response whose session layer resolved a principal.** One middleware at the /api root (`routes/version-header.ts`) stamps the header after the handler whenever a principal is in context, a same-origin refusal included; a session-layer 401, a login redirect, a webhook and the health endpoints carry none, so an unauthenticated caller learns nothing the gated `/api/version` did not already say. Never stamp it in a route.
- **`no-store` on every response of a gated route** — error paths included; it is all per-viewer state (success responses set it explicitly; every error path inherits it from `createErrorHandler`, `src/shared-errors/on-error.ts`, wired via `app.onError`).
- **A cookie principal on an unsafe method proves same-origin.** `sessionLayer`'s cookie branch refuses POST, PUT, PATCH and DELETE unless the request carries `Sec-Fetch-Site: same-origin` or an `Origin` equal to `PUBLIC_BASE_URL`'s origin; absent both it fails closed. The wire is a plain 403 `forbidden`; the ledger says `cross-origin`. Bearer is exempt because it never rides ambient. Logout sits outside the layer (an unknown cookie still answers 200) and runs the same check by hand; a new cookie route outside the layer owes the same. The pure decision is `routes/auth/session/logic/same-origin.ts`.
- **The token refreshes at most once per REQUEST**, shared across every GitHub call in the request (`SessionCredential.renewToken` under the binding the gate builds and hands on as `repoAccess`, so the gate's read, its walk and the route share one renewal) — per-call-site refresh either misses mid-request expiry or refreshes twice.
- **A submit is pending review, threads, submit; a pending review never outlives a failed request.** The review route opens a PENDING review, posts one GraphQL thread per held draft, and submits with the verdict. A thread GitHub rejects (a null thread, or a GraphQL error typed `UNPROCESSABLE`) is folded into the body alone; the response names `commentsFolded` of `commentsTotal`. Any failure after the pending review exists deletes it before the route answers; a delete that fails logs at `warn`. A stale pending review makes the viewer's next create 422; the route deletes it and retries once only when it carries no comments, and answers 409 `pending-review-held` otherwise, because a pending review with comments is the viewer's own unsent work, whether started on GitHub or left by a submit that died mid-way. Every create (the pending review, each thread, the submit, the post-now comment, the reply) rides the binding's retry-off creates, and every pending-review read and write runs on the viewer's token alone: a replayed thread mutation or comment POST is a duplicate comment. A submit whose acknowledgement is lost lists the PR's reviews first; the review this request created showing in a non-pending state means published, and the route answers 201 rather than inviting a second review, while a missing one was deleted and the route 502s. Post-now and submit claim their drafts in the session before calling GitHub: success settles the claim, a failure known not to have reached GitHub releases it, and any other failure keeps it until its lease runs out and the draft is in doubt; no write leaves later than 30 seconds before the lease runs out (a Submit checks before every thread and before the submit), and a write honours a rate-limit wait of at most 20 seconds. An in-doubt post-now looks on GitHub, on the viewer's token alone, for the published comment of every draft its claim holds, then for a review the viewer submitted since the claim whose body holds the draft's folded block, anchor line and body, before posting; a draft found only in the viewer's pending review answers `draft-publish-in-doubt` and keeps the claim, because submitting that review would post it. While a submit runs, octokit's per-token write limiter (which GraphQL reads share) is occupied for about one second per draft, so a viewer-token GraphQL read issued mid-submit queues behind it.
- **Deterministic 400s are an FE contract.** Anything a route rejects deterministically (caps, shape refines) must be mirrored client-side with recoverable copy. The FE resubmits the same state, so an unmirrored deterministic 400 is an unrecoverable loop (see `apps/web/AGENTS.md`). Corollary: validate that every ACCEPTED payload is representable by its own degradation path (the fold-budget refine).

## Audit (enforced, don't weaken)

**One emit, at the choke point.** `src/product-operations/audit.ts` is mounted once at the composition root, ahead of the routes, and writes the audit row for every Product Action and every refusal of one — only a middleware wrapping the gates sees a gate denial, and the router-stamped descriptor names the operation, so new routes are audited automatically. **Never hand-place an emit in a route.**

- **A read is never audited**, denied reads included. Queries fire on every render and already produce an `api.access` line.
- **Ids, tokens and numbers only** — no bodies, no free text. A route that knows the row it acted on calls `stampAuditTarget`; a route whose wire code is a deliberate collapse (the gate's uniform 404) calls `stampAuditReason` so the ledger can say `no-repo-access` while the response still says 404. Otherwise the denial reason is the wire code, stamped by `errorJson`.
- **HTTP status stays out of the row.** `outcome` plus a reason token is the vocabulary; a status would re-introduce the existence leak the collapse exists to prevent.
- `client` is matched against this project's own CLI name — never a `product/version` SHAPE (a caller could write its own address into the ledger). Forensic: **nothing may ever branch on it**, and a derived value must stay inside persistence's `AuditClientSchema` (a store-rejected value throws inside the emit and loses the row).
- `caller_ip` is the socket address, written only under the operator flag.
- **A row is keyed on the world the request acted in**, the `auditScope` the access steps stamp in turn (`stampAuditScope`): the pull request row's world when a row resolved, else the repo's, else the credential's own. An installation world records its id; an owner world records a NULL installation with `source: url` (a url row, a repo in no installation, or a route with no repo such as token mint and revoke). A refusal that resolved no credential at all is not recorded. Documented in `docs/self-host/operations.md`.

## Product Operation catalog

Every domain route declares its operation through the product router — declaration and mounting are one statement, so an endpoint cannot exist without a catalog descriptor. A declaration names its id, its policy and its router-relative path; its classification and method come from the operation table in `packages/contract` (`ProductOperations`), never from the route. Composing the app IS registering: the root commit stamps each declaration's full `METHOD /api/...` endpoint, asserts it equals the table row's method and path (a mismatch throws at composition), and registers it.

Adding or renaming an operation means editing its table row: the table is the only list. Drift fails at composition (`commit()`) and in `test/product-operation-catalog.test.ts`.

The operation table is also one half of a both-directions gate: EVERY operation in it needs exactly one entry in `apps/cli/product-operations.map.json` — a `mergebrief` command, a documented expiring gap, or a reasoned `webOnly` note. Every entry there must in turn name an operation the table carries.
