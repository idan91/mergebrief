# Repo gate (enforced, don't weaken)

- **One gate per request.** The repos router (`routes/repos/index.ts`) mounts ONE method-agnostic gate (`src/access/`) over `/:repoId/*`, so the per-PR subtree, the collaborators leaf and the attachments purge share one positive cache, and the repo list at `/` never meets it. A new route under a repo inherits the gate and never mounts its own (a second gate double-checks access cold and can 404 a just-verified request). The gate sets `repoAccess` (reviewer, repo, footing, push bit, the repo's Installation, the operator pass's PR). The operator rung reads the PR from the path segment after `pulls`, so on the repo-level routes it never opens. The submit and collaborators tests pin single-gate behavior (the gate's repository reads). Behind it the per-PR subtree mounts one access step (`access/pull-request.ts`): a malformed `:prNumber` is the gate's 404, and a `requiresStoredPullRequest` operation gets `pullRequestAccess` (the repo access plus `prNumber`, `rowScope` and the row, a request-start snapshot).
- **The gate names the repo's world.** No credential holds a current installation. After the viewer's token proves read access, `repoAuthzLayer` asks the shared installation resolver (`routes/installation-resolver.ts`) which reachable installation holds the repo; `repoAccess.installation` becomes that installation for the rest of the request. In none, the repo is in no Installation and only its **URL** rows count, so a `requiresInstallation` operation 404s and the row resolution goes straight to the url-box row. Public and private repos alike, cookie and Bearer alike. The resolver's 401 and 502 are the gate's, never cached; a positive entry carries the resolved world and is keyed per credential and repo. The PAT rung below never asks and sets the owner world; `repoAccess.footing` is what steers it, so a per-PR route reading the world without the footing must not exist. The delete route (`repos/pr/delete`) sets `requiresInstallation`: the repository is re-read fresh with the viewer's token and the row deleted only on `permissions.admin` from THAT answer, never the walk's cached bit, and the viewer's shadowed url row at the same coordinates goes with it. The viewer's own pasted row is the inbox domain's session-only purge (`delete-own-pull`): no GitHub call, owner scope is the wall, so a pasted row in a repository nobody can read any more still goes, and both routes share `routes/purge-row.ts`.
- **The gate's second rung is the operator PAT, and it is narrow.** Url-box briefs generate behind a two-key ladder (reviewer token, then `MERGEBRIEF_URL_FALLBACK_TOKEN`); the gate runs the same ladder. It retries ONLY when all five hold: the denial is 404/403, a PAT is configured, the reader owns the PAT (its numeric id equals the id GitHub's `GET /user` answered for the token at boot), the path names a PR, and that PR exists in the READER'S OWN url-box world.
  - `resolveOperatorTokenFor` (`access/operator-token.ts`) is the only reader of `deps.operatorToken`: the gate rung, the binding's `operatorReads`, the paste door and `bindOperatorReader` (the live read's operator reader) all take the token from it. Anyone else gets `undefined`, as does everyone while the owner lookup is pending or after GitHub refused the token: the same answer as an instance with no PAT, so no response may tell them apart. `main.ts` awaits the first lookup (`resolveOperatorTokenOwner`) before it serves.
  - A PAT-carried pass sets `viewerCanPush` false and `footing: operator`; the row resolution then reads only the reader's own url-box rows (the tenant-first probe would hand them the installation's rows).
  - The positive cache carries that footing AND the granted PR. The key is per-repo, so without the PR one pass would clear the gate for every PR in the repo.
  - A converted read reaches the rung through the per-PR binding's `operatorReads` (the owner-world conversation, the span diff, the file range); the row-less attachment read binds `bindGrantedPullRequestGitHub`, the same reach with no known commit. The rung is READS ONLY: every write runs on the viewer's token alone, so GitHub never attributes the operator for a reader's action. The attachment bytes fetch stays outside the bindings: a signed asset URL with no credential, a branch file on the viewer's credential only, a committed file's refs and Contents JSON on the viewer's credential only and its `download_url` with none, never the operator's. One read chooses the operator itself: the live read (`routes/live-read`), whose denials are per alias inside a page that succeeded, which no binding fallback can see; the operator answers only for url rows, never an installation row the same read refreshes. It reads on the viewer's binding and asks an explicit operator reader (`bindOperatorReader`) only for the aliases GitHub showed nothing for or withheld: on PR meta only behind an operator pass, on the Inbox for the owner's own rows. A row withheld from the viewer is never marked unreachable on the operator's word alone. PR meta serves the row the read's own write returned, never the access step's snapshot.
  - A read that sends a caller-chosen ref to GitHub (the span diff, the file range) takes the rung only when every ref is a full SHA in `collectKnownCommits` (`access/known-commits.ts`): the row's base and head, each Brief span, each Delta span. Any other ref reads on the reader's token alone. The binding's `operatorReads` holds this; a route never re-checks it. The file `path` is NOT bound: any path at a known commit is readable.
  - The stack read never takes the rung: the open-PR list names every PR in the repository. A request the gate passed on the PAT gets `{ stack: null }` and no GitHub call.
- **The per-PR row world is resolved, not assumed** (`resolvePullRequestRow`, `access/pull-request.ts`). The repo's Installation is tried first; the url-box fallback is INSTANCE-wide, with a deterministic owner pick (own row first, else the oldest). Per-reviewer state is unaffected: the Review Session's natural key carries the reviewer. The delete route purges the row its access step loaded only when that row lives in the repo's Installation (a url fallback is its 404); the personal list and the inbox's own-row purge stay owner-bound and never use it.
- **Mutations re-resolve the repo fresh.** The gate's cached `repoFullName` is ≤60s stale, fine for reads; a rename + name-reuse inside the window would send a write to the wrong repo. A mutating route fetches `GET /repositories/{id}` with the viewer token immediately before the write. The re-resolve itself answers under the mapper's `collapse` posture (no existence leak); a request the gate passed on the PAT answers its 403/404 as 403 `no-repo-write-access` first. After a successful re-resolve the write's posture is a per-route judgment: `honest` where a FORBIDDEN carries an FE-actionable capability signal (mark-ready, thread resolution, submit, post-now), `collapse` where it carries none (the reply POST). The attachments branch write rides the App's credential under `app-write`: its 401 answers 502, and a rule refusing it answers 403 `attachments-disabled` first. NOT_FOUND collapses to 404 under every posture.
