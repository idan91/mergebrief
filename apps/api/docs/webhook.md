# Webhook (enforced, don't weaken)

- **Verify before parse.** The HMAC is checked against the RAW request body (the exact bytes GitHub signed) before `JSON.parse`, before Zod, before any DB touch. Invalid/missing signature → 401 and NOTHING is written.
- **Tenant from the signed payload.** `TenantContext` derives from the payload's `installation.id` (branded by `github`'s parser, revalidated via `parseTenantContext`), never from a spoofable header. Tenant writes go through persistence's ctx-bound interfaces (`createTenantRepository`, `createIngestRoutines`, `createPurgeRoutines`), and the seen-set through `createWebhookDeliveryStore`; the handler never queries the handle directly. A credential event (`github_app_authorization`) carries no installation: it skips the tenant boundary and touches only the pre-tenant credential rows, through `deleteUserCredentials`.
- **Unlisted owners are dropped** (`routes/webhook.ts`, `OWNER_GATED_KINDS`, the instance-access rule in `sessions.md`). A `pull_request`, `pull_request_review`, `check_run` or `status` delivery whose repository owner is not listed answers 200 unprocessed, with a `warn` (a `debug` for a `check_run` or `status`), except that a close or reopen still lands on a stored PR, and a close re-renders its Entry comment; install and uninstall events still apply. A new kind that starts or wakes a run joins `OWNER_GATED_KINDS`.
- **Fast 200, no compute.** The webhook handler only upserts rows and enqueues one job: no LLM calls, no generation, and no GitHub API call except two kinds of bounded confirmation read, each with no retry and under half of GitHub's delivery budget. Handled and ignored events alike return 200 quickly.
  - A destructive event confirms before it purges (`installation.deleted` reads the installation's presence on the App JWT, `installation_repositories.removed` lists the installation's repositories): GitHub still holding what the event removes is a plain warn and no purge, and no answer in time is a 502 that purges nothing, so a redelivery processes.
  - On a public or internal repo, a reviewer, or a human PR author on either trigger path, whose association GitHub does not trust gets one read of their repository permission, write or admin putting them on the team; a review runs both reads at once, so their bounds never stack. A failure is a warn and 200 with the delivery recorded, and counts them off the team: no checkpoint, and an off-team author's new head projects `awaiting-trigger` with its job still queued, and a head already projected keeps its row. A bot author is never asked; the worker decides for it.
  - A `check_run` (`completed`, or `created` already finished; a run created queued or in progress is ignored) or `status` writes no row beyond the seen-set's record of its signature: it wakes the heads at its SHA through persistence's `recheckHeadsAtSha`, whose rule lives there, since a fork PR's run names no PR and a status never does.
  - A `review_requested` naming a person or a team stamps the PR's `review_requested_met_at` after its trigger (`stampReviewRequestedMet`, set once), so a request removed before any run still meets `reviewRequested`; a bot's request stamps nothing. A submitted review stamps it the same way, before its trigger, when its reviewer earns a checkpoint and is not the PR's author (by login), so the api's permission read, not the worker's association check, decides a private org member's review.
- **Idempotency is inherent, not bolted on.** Natural-key upserts + `job_key = generate:{pull_request_id}` make redelivery safe. On top of them, a `pull_request`, `pull_request_review`, `check_run` or `status` delivery's `X-Hub-Signature-256` digest is recorded after its dispatch succeeds, and the same signature within 72 hours answers 200 unprocessed. A revoke or an install event can repeat byte for byte, so those kinds skip the seen-set (`SEEN_SET_EXEMPT_KINDS`): a purge's confirmation with GitHub guards its replay, and a replayed revoke only forces that user to sign in again; the signature, not the unsigned `X-GitHub-Delivery`, is the key, and a seen-set read or record failure answers 500. Concurrent duplicates both process, so the keys still carry correctness. The key is a leading-edge debounce: `preserve_run_at` keeps the first push's `run_at` and replaces only the payload, and a ready-for-review flip alone refreshes `run_at` (`refreshRunAt`).

## Tests

`test/webhook.test.ts` = integration via `app.request()` against `persistence/testing`'s PGlite harness (real migrations + a `graphile_worker` stub standing in for the real worker schema, tests only; the compose smoke uses real graphile). Payloads follow the shapes in `packages/github/test/fixtures/*.json` and are signed with `@octokit/webhooks-methods` `sign`. Zero network, zero LLM calls.
