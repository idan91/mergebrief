# apps/worker: agent notes

The long-lived background worker. Drains graphile-worker's `generate` jobs, the ones `persistence`'s `createIngestRoutines` enqueues, and produces the PR's artifacts: shared Brief, comparison marks, carry-over hunk spans, revision narrative, and pre-warmed delta cores (one per distinct checkpoint SHA; a span too large for one delta call stores a skip record instead). The generation engine is `brief-core`, reused as-is behind its `Generator` port.

Repo-wide conventions apply (root AGENTS.md); refinements below.

## Map

**Entry points: `src/index.ts`** (the public surface, `exports["."]`; tests + future embedding) and **`src/main.ts`** (the runnable startup wiring, `pnpm start`, deliberately not exported).

What the layout can't show:

- `task/generate/` is the job, and `createRecoverGenerationTask` its lease recovery over the same run. `index.ts` only orchestrates: open the run, decide it once, then brief → ready Entry → revision artifacts → delta cores → finish, settling supersession, shutdown and failure in one catch. `logic/` holds the steps; the run steps take the `RunContext`, the per-run value built once. `logic/run-decision` is the only caller of the spend gate's claim (`applySpendGate`, `refuseAtCap`); a stored-brief run is charged at its first paid call (`createSpendCharge`) and a large run claims its units before its detail calls (`claimRunUnits`), and the Entry comment's body builders stay in `task/entry-comment/`.
- `task/github-port.ts` is the GitHub boundary: `PullRequestSource`, the PR-bound reads a job makes, over `packages/github`'s bindings (`GitHubBinders`; `main.ts` passes the App's, tests the `github/testing` fake). An installation job reads through `bindInstallationGitHub` and alone carries `entryComments`. A url-box job reads through `bindReviewerGitHub` on the grant-resolved viewer token, with no renewal; one probe decides the whole job, and a 404/403 switches every read to `bindOperatorGitHub` on the operator PAT. The PAT comes from `packages/github`'s config, and `main.ts` awaits its owner lookup before the runner starts; the switch opens only when the payload's `owner_user_id` owns the PAT, otherwise the job runs as if no PAT were set. A denied probe while the lookup is still pending throws transient (`github-unavailable`) so graphile retries. On the PAT the open-PR list answers empty, so the brief resolves no stack: that list names every PR in a repository the owner cannot see. A ticket in another repository, and that repository's visibility, answer not-found unsent, so the PAT reads no issue outside the job's repository.
- `logic/lockfile-summaries/` reads each changed pnpm, npm or yarn lockfile at the diff's merge base and head (a revision span reads its two heads, each beside its own merge base when they differ, so only the PR's own change moves; a rebase's base-side package move stays out, and a merge base it cannot read leaves every lockfile unread), and summarizes it in a forked child process (`summary-child.ts`) with its own `--max-old-space-size`, an empty environment and a span deadline: lockfile text comes from the PR head, and a hostile one may only cost that child. A child that times out or exits reads the lockfile as unparseable, which fires `changes-package-source`.
- `runner.ts` owns boot order (app-schema → queue-schema migrations) and the long-lived graphile runners: the first drains `generate`, `recover-generation`, `sync-entry` and the scheduled sweeps on `WORKER_CONCURRENCY` slots and alone carries the crontab; the large pool's runner drains `generate-large` and `recover-generation-large` on `WORKER_LARGE_CONCURRENCY` slots (default 1) with its own pool sized to them. `main.ts` builds the large pool's tasks from the same factories with `{ pool: RunPools.LARGE }` (`buildLargePoolTaskList`).
- **A multi-call run** (`logic/generation-parts.ts`) hands brief-core's `generateBrief` the worker's hooks: `onGroupingDone` claims one unit per detail call the engine reports missing, a stored part its detail schema no longer parses included (`claimRunUnits`; refused, the run ends `capped`), then records the plan on the attempt row (`recordPartsPlanned`: every detail call as the total, the stored ones as already done, so the waiting card's count reads the same N as the Entry on a resumed attempt); `loadPart` answers from the span's stored parts (read once per run; the parts are wiped first when no `grouping` part is among them, since only that grouping planned their batches, or when the grouping part's `gitAttributesDigest` is not the default branch's `.gitattributes` of this run, since another file shortens other files), and `onPartDone` writes the part (`generation_part`, keys `grouping`, `detail:<n>`, `detail:<n>:<half>`) and counts a completed detail call on the attempt row (`recordPartDone`); a grouping part that ran fresh first deletes every detail part the span holds, whole and halves, since only that grouping planned their batches, and the units then count every call again. A multi-call run anchors like a single call: the hop lands from `onPlan`, the brief keeps the decided anchor, and a grouping part resumes only under the anchor plan it was grouped over (`anchorPlanDigest`: the previous brief's head and index and its carry, fixed by `loadStoredParts(previous)` before any hook runs). A hook's own throw is classified before it crosses the engine: a run signal or a stamped failure passes as it is, anything else (a store or Postgres error) is `TransientJobError`, so graphile retries and the parts already paid for stay; `runGenerator` keeps a run signal's class the same way. The span's parts are deleted right after the brief write, by a run that finds the pair's brief stored, and when a permanent failure lands after every missing detail call stored its part (the merge or the write failing over the stored parts would fail the same way on every resume, so a re-trigger regenerates); those three deletes only warn when they fail, since the next run over the stored brief sweeps what is left, while the wipes of stale parts before any detail call still fail the run. Any other failure, whatever the code, keeps them for the retry or the re-trigger, and `sweep-generation-parts` bounds what neither comes back for. `logic/git-attributes.ts` reads the DEFAULT branch's `.gitattributes` (never the PR head) for the engine's generated and vendored files, three ways: content, none (absent, over its cap, or refused for good, as not text, not a blob or a permanent GitHub error: every file is read in full, and the parts digest is the empty file's) and unread (a failure a retry may clear: the engine still reads every file in full, but a run over a span holding parts, and a multi-call run over an empty one, ends transient as `github-unavailable` before any paid call, keeping every stored part for the retry, so no part is ever stored or wiped under a digest of a file the run never saw; a single call over an empty span runs). The span's parts are read before the generating phase (`loadStoredParts`), outside the engine's single-call check, which reads a hook's throw as nothing stored, so a store error ends the run transient there too. `deps.detailConcurrency` and `deps.forceMultiCall` (`generator.detailConcurrency`, `generator.forceMultiCall`) ride through to the engine; the call plan itself is the engine's.
- **Pool routing** (`logic/pool-routing.ts`) runs after the PR read and the author gate, before the claim (a gated run posts its on-demand Entry from the pool it landed in, never queueing for a large slot): a normal-pool run whose counts predict multi-call (`predictCallPlan`: more than 120 changed files, or additions plus deletions past 400k tokens at 67 bytes a line) moves its job to the large pool through persistence's `routeToLargePool` under the same job key and ends with nothing claimed, recorded or marked; when an unlocked job already waits under the key it stands down the same way. A large-pool run never moves, a wrong guess runs where it landed, and a run over the pair's stored brief stays. A recovery run routes the same way under the head's recovery key once `shouldRecoverClaim` found a claim to take over, before anything is marked.

## Invariants (enforced, don't weaken)

- **Payload handshake:** the job payload shape is the shared `GenerateJobPayload` union in `types`: string ids, snake_case. An App-installation job carries `installation_id`; a url-box job carries `owner_user_id` + `grant_id` (a credential REFERENCE, never token material). Task ids come from `types`' `QueueTasks`. The shape changes additively, per the rule on `GenerateJobPayload`: a queued job outlives the release that wrote it, so the parser (`src/task/payload.ts`) takes a new field as optional, and the compile-time pin there breaks the build when the parser requires a field the contract does not guarantee. It cannot see jobs already queued, so review holds the additive rule. The optional `traceparent` is read apart from the job's fields (`readPayloadTraceparent`), so a bad one costs the span link, never the job; every task `buildTaskList` registers runs through `traceJob`, one root OTel span per job linked to the enqueue.
- **Tenancy:** everything goes through persistence's ctx-bound interfaces (`createTenantRepository`, `createArtifactStore`, `createGenerationProjection`); the scope identity (installation or url-box owner) enters ONLY via the validated payload, never a spoofable source.
- **Url-box jobs never write to GitHub:** the Entry-comment surface is off entirely for them, and the viewer token is used for reads only, decrypted lazily per job, held in the bound source's closure, never persisted or logged.
- **Abort is not a failure**: supersession → terminal `superseded`, `attempts` untouched, NO graphile retry, no salvage/dump. A shutdown releases the claim and hands the job back to graphile, except on the job's last attempt: no retry follows, so the run ends `failed` as `attempts-exhausted` like any last attempt.
  - **A multi-call run is pinned once its first detail call starts** (`watch.pin()` from the engine's `onDetailStart`): a moved head is recorded on the watch, never thrown, the poll and the pre-call checks stop reading the head there (the tick renews the lease alone), the lease keeps renewing, the run finishes on its own head and ends `succeeded` with no `superseded` mark, and its narrative and delta cores are still written. Every Entry post of such a run reads the head fresh first and stands down on a moved one; the newer head's run owns the thread. A fresh read that finds the run's own head again (a push, then a push back) undoes the recorded move: the post goes up and the poll resumes. A url-box run schedules the observed head once it ends, succeeded or failed for good, as every supersession path does; an installation's push webhook already queued it, and a retried failure leaves it to the retry's PR read. A lost claim still ends a pinned run. A run that would write a brief and finds another head of the PR under a live claim (`readOtherHeadLeaseMs`) stands down and re-queues for one head poll later, or the lease's end if sooner: a brief written beside a pinned run would take the head index that run derived at open, and an unpinned holder ends superseded within a poll.
- **No double-spend:** brief cores are skip-if-stored; a narrative or delta core is skipped when stored under marks written from the bases resolved now (below); marks and narratives are content-addressed upserts. A retry pays only for what a prior attempt didn't finish, with one exception: a run that stops between a core's write and its key's marks write pays that core again, and the longest such window is a stale delta sharing the revision key, whose rewrite sits between the narrative and the marks.
- **A span key's marks never certify a core computed from other bases** (`logic/span-marks.ts`). Over a key with no marks, narrative or delta stored, the revision span's marks go first, so a run stopped at the narrative (a push, the cap, a last-attempt shutdown) still leaves the span readable and a later run of the head writes the narrative. Otherwise they follow the narrative at once, unless a checkpoint shares the key and a delta is stored there: that key runs first in the delta loop and its marks follow its delta. A checkpoint's own key writes its marks after its delta. The row stores the bases the span was read against, and a stored narrative or delta is kept only under marks written from the bases resolved now; a same-head retarget or a returning head rewrites all three. Stale marks are dropped right before the first rewrite under the key (narrative, delta or either skip record), so a run that stops between that rewrite and the marks write leaves the key unmarked, never marked from other bases. A narrative that fails over marks that are not current, stale or absent, or a stored brief that cannot be read back, withholds the marks and leaves the shared delta as stored, so no row certifies text it was not computed with.
- **Write checks are warn-only:** each Brief, Delta Brief and Revision narrative runs its `brief-core/artifact` write check before the write (`logic/artifact-check`); a failure logs `artifact.check.fail` with `kind` (a `GenerationKinds` value, as on `generation.complete`), `issueCount`, `firstPath` and the generated body is written unchanged. A Brief's check accepts this run's custom risk names plus the tokens on its carried chunks. Stored Briefs are read back only through `readStoredBrief`; an issue's `message` is never a log field.
- **No secret leaves through the output:** `main.ts` wraps the generator in `guardGeneratorOutput` (`logic/output-secret.ts`) over every secret value the worker holds, so a Brief or Delta Brief carrying one fails as `output-secret`, permanent, and a Revision narrative carrying one is dropped with the Brief unaffected; the log names the field and env var, never the value. The guard screens every attempt (`screenAttempt`) before the floor validates, salvages, warns or retries, so an attempt holding a secret ends the run at once; it also masks the `log`, `onWarning` and failure-dump `redact` channels, failing the run when any of them saw one, and a failure whose message carries one fails the same way. Each secret of at least 12 chars is matched raw and JSON-escaped; one with at least 6 distinct chars also as hex and as base64 at any alignment, and with any spacing or line wrap, except that letters alone, which prose can spell by accident, match only spaced one char at a time. The scan is literal, so a reversed, doubly encoded or punctuated-apart secret passes, and so does a letters-only one in longer groups or line-wrapped. The secrets are every secret-named env var, each OTLP headers var with its header values and bearer or Basic credentials apart, as written and decoded, plus each var the instance config names as a credential (`listCredentialVars`: `generator.apiKeyEnv`, every `contextSources[].tokenEnv`).
- **Error classification:** permanent failures (404/406, deterministic generation failures, persistence's `ScopeViolationError` and `InvalidArtifactBodyError`) are marked `failed` and NOT rethrown; transient ones (429/5xx/network) are marked and rethrown so graphile owns retry/backoff. `logic/job-failure.ts` reads the thrown class once and decides the retry.
- **`main.ts` is the composition root and the only reader of `process.env`** besides `instrument.ts`, the telemetry preload (`--import` ahead of `main.ts` in `pnpm start` and the image), which reads the `OTEL_*` config only and starts `logging/tracing`; `main.ts` stops it after the pool closes; both load `apps/worker/.env`, then the workspace root's `.env` (`src/env-file.ts`), keeping a value already set, and `main.ts` then names the workspace root's `mergebrief.config.yaml` in `MERGEBRIEF_CONFIG` when the variable is unset and the file exists (`applyDefaultConfigPath`); everything else takes `env` or its values as parameters (`loadConfig(env)`, which also parses `WORKER_CONCURRENCY` and `WORKER_LARGE_CONCURRENCY`, the two runners' slot counts, default 1 each, resolves `generator.detailConcurrency` to `DEFAULT_DETAIL_CONCURRENCY` (8) when the block omits it, and reads `generator.revisionNarrative` and `generator.hugeSpanRatio`, each at its brief-core default when the block omits it), brief-core's helpers included. The generator block comes from the instance config (`MERGEBRIEF_CONFIG` → `mergebrief.config.yaml`, else zero-config defaults); BYOK keys resolve by env-var NAME (`generator.apiKeyEnv`), never from DB or repo config. The tracker root is built there too (`GenerateTaskDeps.trackerRoot`: the env and the `contextSources:` block, tokens by env-var NAME) after `checkTrackerBoot` refuses boot on a listed tracker or default board it cannot read, or on a listed Jira `site` Atlassian answers no site for (`jira-access.ts`; an unreachable Atlassian and every token answer let boot go on); the task binds GitHub's transport per job (a url-box job's to the PR's repo; an installation job's to that repo and its `issuesRepo`, unless the instance config's GitHub tracker entry sets `siblingRepos`; every job names the PR's repo as `pullRequestRepo`, and `issue-api.ts` ranks visibility private, internal, public, so an issue is never read from a repository less widely visible than the PR's; a transferred issue reads `not-found` under any bound, since `github` refuses its redirect; a repo's own `issuesRepo` is its default-branch writers' choice, trusted like the rest of its settings), offers Notion's and Jira's only to installation jobs, Jira's one per process (`GenerateTaskDeps.jiraTransport`: the instance remembers the site's cloud id), and resolves one read per bound slot when a core needs the ticket.
- **Repo-config is fail-open:** nothing in the `.mergebrief/` phase may fail a generation, except the pre-claim `settings.yaml` read of the author gate (a bot PR), which retries a transient failure while attempts remain (below). Both pre-claim gates first read a transient failure again in the run (`acquireGateRepoConfig`: after 250 ms, 750 ms and 1.5 s), spending no attempt and writing no row between tries; the trigger-condition check then applies the instance's conditions alone. Fetch failures become loud `fetch-failed` outcomes, invalid files are rejected whole, and an unexpected crash degrades to no-config. Per-file outcomes are recorded on the generation row BEFORE the model call; the policy snapshot rides the brief artifact.
- **Entry-comment draft gate:** the Entry comment posts on draft PRs unless `.mergebrief/settings.yaml` sets `entryCommentOnDrafts: false`; the delete-only sweep runs ONLY on that explicit off (a settings fetch failure suppresses posting on a draft but never deletes a live comment).
- **One Entry comment per PR:** every write of the PR row's Entry id is a compare-and-set from the id the run last saw (`swapEntryComment`). A post whose swap loses deletes the comment it just made, best-effort, then tracks the row's id as live but not as its own, and deletes it only after a fresh head read confirms its own head (a moved head leaves it, a failed read leaves it to the head's sync). The winner's body may be stale, so a terminal post or a sync that loses its swap, or finds the row tracking a comment it never read, queues the head's sync, which renders the Entry again from the head, the row and the stored brief read fresh; a sync that finds its body live queues nothing more. A sweep whose clear loses leaves the winner's id. A post tells which live body it may replace by the marker and the hidden kind token after it, which carries the head's sha (`isHeadEntryBody`, `isOnDemandEntryBody`), never by the body's text, whose copy, rev link and reset time vary; a marked body with no readable token is unsettled and names no head, so the next write that replaces an unsettled body rewrites it; the closed body is replaced only by a post that read the PR open or by the sync's ready body over that head's stored brief, and an unmarked body is left. Every Entry body ends in a hidden marker, and each tracked post lists the PR's comments and deletes the marked ones older than it by the same author: what a run killed between its post and its swap left. A newer marked comment is a later run's mid-swap and stays.
- **The failed Entry is terminal-only:** a run that ends `failed` with no retry to follow (permanent, graphile's last attempt, or the head's claims spent) posts the failed body, built from the code alone, never `params.detail`. Under the Entry gate it replaces this head's generating, capped or earlier failed body, on a head it read as current the on-demand body and the closed body a reopen outdated too, or creates the comment while the PR row names none another run posted, and leaves every other live body; a stored brief keeps its ready body. Every Entry post after the PR read first reads the head: a moved head leaves the thread to the newer head's run. On an unread head the generating, ready and failed posts only replace a live body that names this head, the capped and on-demand posts stand down, and the run goes on. A run that failed before reading the PR knows no gate, so it only replaces this head's own bodies. A retrying failure, a lost claim, supersession, the cap and shutdown post nothing, and a comment error only warns. Ahead of any write that ends a run `failed` (an exhausted claim's own, in its transaction), and after a ready, on-demand, capped or failed post that GitHub failed in a way a retry may clear, that lost its swap, or that stood down on an unread head (a ready post also on a draft's closed Entry gate), the run queues the head's Entry sync (`sync-entry`, keyed per head, ten attempts on graphile's backoff); the api queues it as well when a PR with a tracked Entry comment closes. The sync renders the Entry from the row through the same compare-and-set: the ready body over a stored brief for the head (on an open PR one at the current base, the run's own test, so a retargeted head's failure keeps its failed body; on a closed one at any base), the closed body (replace-only) on a closed or merged PR, else the failed, on-demand or capped body the row names, the capped one recreated only where the PR row still tracks a comment; a pending, running or superseded row, or on an open PR a moved head, leaves the thread. On an open PR whose head it read as this one, the ready, on-demand and capped bodies replace any marked body, as the run's own posts do; the failed body replaces only what the failed post does, so an older head's ready Entry stays. A closed or merged PR renders GitHub's last head and replaces any head's generating, failed, capped or on-demand body, since a PR closed inside the debounce window gets no later run; over a stored brief its ready body also replaces that head's closed body, which a close sync posts while the run still generates. Nothing it posts creates a comment on a PR that is no longer open. A failure a retry may clear throws for graphile's retry, a draft's unreadable `settings.yaml` included (the run's own post stands down there; the sync exists to land it), and the last attempt logs `job.retries.exhausted`; a refusal for good (a 401, 403 or 404 write, a row outside the scope) ends the sync with a warn. A sync that cannot queue its successor throws for graphile's retry.
- **The author gate runs before any claim** (`logic/author-gate`): a head ingest projected `awaiting-trigger` posts the on-demand Entry under the Entry gate and ends. A bot PR with no Trigger approval goes on only when the default branch's `settings.yaml` lists its login in `trustedBots`; unlisted or unreadable, the run marks the row `awaiting-trigger` and posts the same body. The mark takes the pull request's row lock, as an approval does, and refuses a PR approved since the run read it; that run stands down and the approval's job runs the head. A head ingest held before an approval goes back to `pending` with a fresh job (`releaseApprovedHold`) instead of posting. A settings read that still fails transiently after the in-run tries retries while graphile has attempts left, the row reading `failed` as `github-unavailable` between attempts, since the hold it would otherwise write waits for a person; a refused read or the last attempt holds. A gated run takes no claim, records no attempt and reaches no model, and no failure moves an `awaiting-trigger` row, not even one thrown before the run read it (the store's unclaimed marks answer `status-kept`), so a retry meets the gate again. Url-box jobs, recovery runs, a stored brief's run and a succeeded row are never gated. The on-demand body names no head, so a later push finds it live and does not re-ping. The post re-reads the row first and leaves a head a click already moved on to the run the click queued, and it checks the head like every Entry post and, as the capped post does, stands down on an unread one. Persistence's `claimRun` refuses an `awaiting-trigger` row as well: the backstop behind this gate, never its replacement.
- **The trigger-condition check runs after the author gate, before pool routing and any claim** (`logic/condition-check`): the instance's and the default branch's `triggerConditions` merge per kind, a settings read a retry may clear is read again in the run, never through graphile (a refused read or the last try applies the instance's alone), a `paths` condition reads the PR's file list here only when it can decide the verdict (not while another plain condition is unmet, whose hold then lists no `paths` item, nor any `any` group holding one, until the others pass, nor while an `any` group with no `paths` member holds the head with every member unmet, its `bots` and `ci` members judged on the reports read before the file list, nor for an `any` group another member meets), failing as the run's own read would and handed on so the run never reads it again (a run bound for the large pool leaves it unread, so `paths` reads as met, the run routes, and the large pool's run reads the list once and decides), and matches a rename by its new or old path (the old one never reaches `buildPrMetadata`'s generation input) among the files GitHub lists, at most 3,000, so a larger PR matches on those alone, a `bots` or `ci` condition alone reads the head's check runs and statuses (plus reviews for `bots`, the base's ruleset-required checks for `ci: required`) once each, a 403 on the check-run or status read holding as the permission missing, never failing (each read carries its own flag: `clean` and a ruleset check pinned to an App, which counts only that App's runs and no status, read the check-run one; any other `ci` name passing on one source while the other was refused holds as missing), and an unmet condition marks the row `held` with every unmet item (`markHeld`), logs `generation.hold` and ends: no claim, no attempt, no model. `reviewRequested` and `paths` stay met for the PR once met, from the PR row's stamps (persistence's `readConditionStamps`, read from the row pickup loaded): `reviewRequested` by a pending request, its stamp, or a submitted review other than a bot's or the PR's author's, on a private (not internal) repository from anyone, elsewhere from an owner, member or collaborator (`TRUSTED_AUTHOR_ASSOCIATIONS`, no permission read; the api's review webhook stamps a reviewer its permission read trusts, so this is the fallback for a review the webhook never stamped) (the review list read only when neither of the first two holds, shared with `bots`), and `paths` by a stamp under the current globs' digest (`digestPathGlobs`, sorted and deduplicated), which skips the file list read, else by a match, scanned once per run (`addPathsMatch`) and read by both the verdict and the stamp. A run writes the stamp a condition seen met by evidence owes (`deriveOwedStamps`) before it holds or claims, only where the row lacks it, and a failed write warns and the run goes on; a stamped member counts inside `any`. A hold the store refuses stands the run down. Url-box jobs, recovery runs, a stored brief's run, a succeeded row, a head a Generate click stamped and a PR generating on every push (`generate_every_push_at` set) are never checked; a hold the store refuses because the switch went on after pickup goes on to the claim, since the switch queues a job only for a head it finds held. A kind with no check in `evaluate.ts` is met. Under the Entry gate the held body (`entryComment.held.*`, third-party text as fenced inline code) edits an existing Entry comment in place, so nobody is notified again; a PR with no Entry gets one posted. It writes over any marked body but this head's closed one and is left alone when the live body already matches; a closed body it leaves queues the head's sync, which reads the PR fresh; the post re-reads the row and the head as the on-demand post does (`logic/status-entry`), and the sync rebuilds it in place from the row. Every generating post edits this head's live held or generating body into the generating one, on an unread head too and on a retry or recovery run whose row reads `failed` or `pending`, so a released hold's ready post is its one ping and a retry after the generating post landed pings no second time; any other live body is reposted as usual. The held post, the generating post on a current head, its in-place edit on an unread head and the large run's generating edit each read the head again once the write lands, since a newer head's body posted in between is gone under it: a moved head gets its own Entry sync. A failed read queues nothing, since this head's sync stands down on a moved head, so the thread keeps the body until the newer head's next Entry write.
- **The daily generation cap gates ONE boundary**: `applySpendGate` claims the row through `projection.claimRun` before any provider call, so a run never counts itself. The gate sits after the GitHub read and the brief lookup: a job whose base and head pair already has a stored brief takes no claim while no claim names its row (a claim live or lapsed sends it through `claimRun`, where it answers `running` or takes the lapsed claim), counts only if it pays (its first provider call is charged under the cap lock through `chargeRun`; refused there, it logs `spend.cap.trip` and stands down without a claim), and settles a row no run holds through `settleStoredBrief` however it ends with no retry to follow: success, the cap at either check, or a failure for good. No run marks a `succeeded` row `failed` or `superseded`, not even one that throws before reading it. Such a run may still owe a checkpoint delta or a narrative, so at the cap a count-only check refuses it before any provider call. A run ingest did not project (the live base moved past the stored one) projects itself before the gate.
  - `claimRun` claims the row with a run id and a lease (`CLAIM_LEASE_MS`) renewed on the head-poll tick, and queues the head's `recover-generation` job for after the lease in the claim's own transaction. Only a claim records an attempt, a graphile retry's included; a head takes at most 3 claims between triggers, and the fourth is `exhausted`: it logs `job.retries.exhausted`, and the claim itself has ended the row `failed` as `attempts-exhausted` (an earlier failure stays), or settled it when the brief is stored, with the head's Entry sync queued. The run never marks the row after a refused claim; it posts the failed or capped Entry only for the end the claim returns, and re-reads the row after the head read, standing down when a trigger moved it. A `hopeless` claim (the row failed with a Cannot-help code) stands down without a write, a post or a retry, and a condition hold over such a row is refused the same way. Every later row write is fenced by the run id, and a lost claim stands down without a write or a retry. A recovery run claims the row even over a stored brief, and its claim queues the head's next recovery job like any claim; the same key ends this job's own retries, so a takeover that fails transiently or meets a shutdown hands the row back (`awaits_recovery`) and posts nothing, and the next recovery job reruns it, the claim budget ending the chain. A recovery job runs only a lapsed claim or a handed-back row, never a row a regular run left. It marks nothing before the claim step, and a throw there fails the row like any run; once its attempts end unclaimed, it ends `failed` (`attempts-exhausted`, or a permanent failure's code) the lapsed claim it found, through `endLapsedClaim`, or the `pending` row a takeover's shutdown handed back, through `endReleasedClaim`, or keeps the failure a takeover handed back, and posts the failed Entry; a moved head ends either `superseded`. The dead holder's own job stays locked for 4 hours, and any `add_job` on its key before then detaches it with its attempts spent; the attempt budget and the stored-brief path bound what it can still pay.
  - At cap the run is SKIPPED: terminal `capped` (not `failed`, no retry, no attempt consumed), written by the claim, `evt: spend.cap.trip` at warn. The Entry comment is UPDATED only if one exists and no brief is stored for the pair, never created; a row already marked `failed` keeps that status. `spend.maxGenerationsPerDay` is one number and `spend.cap.trip` still carries `repo`.
  - A claimed run that succeeds with no provider call (a brief carried over an unchanged span, a takeover with nothing left to pay) gives its units back through `refundRun` before its success write (its attempt row stays at 0 units), so it costs the cap nothing; its claim still counts toward the head's 3 attempts.
  - A large run claims its detail calls' units through `claimRunUnits` (persistence's `claimUnits`, under the cap lock). Refused, it ends its claim `capped` with `{needed, left, cap}` as the row's `error_params`, logs `spend.cap.trip` with them, updates the Entry as the cap does with a heading that names them, and stops through `SpendCappedSignal`. A run needing at least the whole cap fits no day, so its Entry names the cap instead of the next push.
- **Scheduled jobs are instance-wide and worker-only**: each runs on graphile's cron (its `*_CRONTAB` line joined into the runner's `crontab` in `main.ts`) and calls a persistence sweep that takes the handle, never a ctx, except the reconcile job below, which calls GitHub. Nothing on a request path may call one.
  - `reconcile-webhook-deliveries` (every 15 minutes) reads the App's delivery log on its JWT and asks GitHub to resend what failed. It holds no state: `logic/select-redeliveries.ts` decides from the log alone, per `guid`, skipping any success, a 400 or 413, an original past 71 hours or out of view (its attempt count is unknown), a `github_app_authorization` (its delete has no confirmation, so a replay would end a later sign-in) and a `pull_request` or review its installation has a later removal for, dated by the removal's earliest attempt in view (a replay would recreate purged rows, and a retry's time is not when the removal happened), waiting 15 m, 1 h, 4 h then 12 h from the last attempt and stopping at 5, at most 20 a tick from at most 100 pages of the log (a failure older than the last page read is never seen). A read the cap stops then lists up to 10 pages of GitHub's failed-only log (`status=failure`, codes 400 to 599, so a never-connected attempt is not among them), so a tick lists at most 110 pages, 440 list requests an hour on the App JWT, and warns when a failure past the last page read, inside the 71 hours, is not a `check_run` or `status`, or when the pages read hold a never-connected attempt, since an older one past them is out of sight; otherwise it logs at info, a `check_run` or `status` (it only wakes a head to check it again) after every other due delivery. A failed list, a 422 or a rate limit warns and waits for the next tick; one delivery's refusal warns and moves on.
  - `sweep-audit` (daily) calls `sweepAuditLog`; retention is an operator env setting. Unset retention deletes nothing; a window under the 30-day floor is refused.
  - `sweep-sessions` (hourly) calls `sweepExpiredSessions`, then `sweepDeadCredentials` (dead grants, and tokens 30 days past revoke or expiry), always on: an expired session or dead token grants nothing. Each batch hands its orphaned grants over once committed, and the task revokes every one at GitHub in a `finally`, so a later failure still revokes what earlier batches removed. Revokes run three at a time inside a 30-second budget (`REVOKE_BUDGET_MS`) so a GitHub outage cannot hold the job slot; the rest are skipped with one warn naming the count, since the grants are gone and GitHub expires the tokens on its own. A failed revoke warns `grant.revoke.fail` and the sweep stands.
  - `sweep-webhook-deliveries` (hourly) calls `sweepWebhookDeliveries`, always on: a delivery past the 72-hour window suppresses nothing.
  - `sweep-generation-parts` (daily) calls `sweepStaleGenerationParts`, always on: a span whose newest part is over a week old goes whole, unless a live claim holds its head. A superseded, capped or failed run's parts have no other end short of the pull request's cascade.
  - `sweep-pull-requests` (daily) calls `sweepClosedPullRequests`; retention is the instance config's `retention.pullRequestDays`, read by close time across both scope worlds. Unset retention deletes nothing; a window under one day is refused.
- **Migrations at boot are idempotent** and ordered app-schema → queue-schema (`startWorker`), both inside persistence's migration lock through `ensureAppSchema`'s `migrateQueue`; the `graphile_worker` schema stays graphile-owned.
- **Failure dumps are swept per process, not by a queue job** (`failure-dump-sweep.ts`): at boot and once a day each worker deletes the `*.failed.json` files in its own dump folder (`FAILURE_DUMP_DIR` in `main.ts`) once they are seven days old, always on. The folder is the container's own disk, so a cron job, which one replica claims, would leave the other replicas' dumps in place; no retention setting or purge reaches it.
- **One process logger**: `main.ts` builds it; the task takes it via `GenerateTaskDeps.log` and stamps `{prId, headSha}` child bindings on every job line; graphile lifecycle logs ride `createGraphileLogFactory`.
  - The first-class `evt` names this worker mints: `job.fail`, `job.retries.exhausted` (`attempts === max_attempts`, or a head's claims spent), `provider.error`, `spend.cap.trip`, `artifact.check.fail`, `generator.tool-access` (boot, codex or cursor), `generator.plain-http` (boot, a `generator.baseUrl` on plain http to another host), `link-fetch.public` (boot, `linkFetch.mode` public), `jira.token.check` (boot, a listed Jira site whose token Atlassian refused or answered beyond `read:jira-work`), and `grant.revoke.fail` (shared with the api).
  - JOB/PROVIDER failure logs are MESSAGE-ONLY (no `err` field): provider cause chains may carry request contents, and the URL scrub targets URL-shaped secrets, not prompt/diff payloads. Boot failures (`main.ts` catch) are exempt: nothing provider-shaped reaches them, and the `err` field keeps the stack the operator needs.
