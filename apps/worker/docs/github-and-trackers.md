# GitHub and trackers

- `task/github-port.ts` is the GitHub boundary: `PullRequestSource`, the PR-bound reads a job makes, over `github`'s bindings (`GitHubBinders`; `main.ts` passes the App's, tests the `github/testing` fake). An installation job reads through `bindInstallationGitHub` and alone carries `entryComments`. A url-box job reads through `bindReviewerGitHub` on the grant-resolved viewer token, with no renewal; one probe decides the whole job, and a 404/403 switches every read to `bindOperatorGitHub` on the operator PAT. The PAT comes from `github`'s config, and `main.ts` awaits its owner lookup before the runner starts; the switch opens only when the payload's `owner_user_id` owns the PAT, otherwise the job runs as if no PAT were set. A denied probe while the lookup is still pending throws transient (`github-unavailable`) so graphile retries. On the PAT the open-PR list answers empty, so the brief resolves no stack: that list names every PR in a repository the owner cannot see. A ticket in another repository, and that repository's visibility, answer not-found unsent, so the PAT reads no issue outside the job's repository.
- `main.ts` builds the tracker root (`GenerateTaskDeps.trackerRoot`: the env and the `contextSources:` block, tokens by env-var NAME) after `checkTrackerBoot` (`tracker-boot.ts`) refuses boot on a listed tracker or default board it cannot read, or on a listed Jira `site` Atlassian answers no site for (`jira-access.ts`; an unreachable Atlassian and every token answer let boot go on).
- The task binds GitHub's transport per job (`logic/ticket-context.ts`): a url-box job's to the PR's repo; an installation job's to that repo and its `issuesRepo`, unless the instance config's GitHub tracker entry sets `siblingRepos`. Every job names the PR's repo as `pullRequestRepo`, and `task/issue-api.ts` ranks visibility private, internal, public, so an issue is never read from a repository less widely visible than the PR's. A transferred issue reads `not-found` under any bound, since `github` refuses its redirect. A repo's own `issuesRepo` is its default-branch writers' choice, trusted like the rest of its settings.
- The task offers Notion's and Jira's transports only to installation jobs, Jira's one per process (`GenerateTaskDeps.jiraTransport`: the instance remembers the site's cloud id), and resolves one read per bound slot when a core needs the ticket.
