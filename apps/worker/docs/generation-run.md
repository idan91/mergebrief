# Generation run

- `task/generate/` is the job, and `createRecoverGenerationTask` its lease recovery over the same run. `index.ts` only orchestrates: open the run, decide it once, then brief → ready Entry → revision artifacts → delta cores → finish, settling supersession, shutdown and failure in one catch. `logic/` holds the steps; the run steps take the `RunContext`, the per-run value built once. `logic/run-decision` is the only caller of the spend gate's claim (`applySpendGate`, `refuseAtCap`); a stored-brief run is charged at its first paid call (`createSpendCharge`) and a large run claims its units before its detail calls (`claimRunUnits`), and the Entry comment's body builders stay in `task/entry-comment/`.
- `logic/lockfile-summaries/` reads each changed pnpm, npm or yarn lockfile at the diff's merge base and head (a revision span reads its two heads, each beside its own merge base when they differ, so only the PR's own change moves; a rebase's base-side package move stays out, and a merge base it cannot read leaves every lockfile unread), and summarizes it in a forked child process (`summary-child.ts`) with its own `--max-old-space-size`, an empty environment and a span deadline: lockfile text comes from the PR head, and a hostile one may only cost that child. A child that times out or exits reads the lockfile as unparseable, which fires `changes-package-source`.
- `runner.ts` owns boot order (app-schema → queue-schema migrations) and the long-lived graphile runners: the first drains `generate`, `recover-generation`, `sync-entry` and the scheduled sweeps on `WORKER_CONCURRENCY` slots and alone carries the crontab; the large pool's runner drains `generate-large` and `recover-generation-large` on `WORKER_LARGE_CONCURRENCY` slots (default 1) with its own pool sized to them. `main.ts` builds the large pool's tasks from the same factories with `{ pool: RunPools.LARGE }` (`buildLargePoolTaskList`).
- **A multi-call run** (`logic/generation-parts.ts`) hands brief-core's `generateBrief` the worker's hooks: `onGroupingDone` claims one unit per detail call the engine reports missing, a stored part its detail schema no longer parses included (`claimRunUnits`; refused, the run ends `capped`), then records the plan on the attempt row (`recordPartsPlanned`: every detail call as the total, the stored ones as already done, so the waiting card's count reads the same N as the Entry on a resumed attempt); `loadPart` answers from the span's stored parts (read once per run; the parts are wiped first when no `grouping` part is among them, since only that grouping planned their batches, or when the grouping part's `gitAttributesDigest` is not the default branch's `.gitattributes` of this run, since another file shortens other files), and `onPartDone` writes the part (`generation_part`, keys `grouping`, `detail:<n>`, `detail:<n>:<half>`) and counts a completed detail call on the attempt row (`recordPartDone`); a grouping part that ran fresh first deletes every detail part the span holds, whole and halves, since only that grouping planned their batches, and the units then count every call again. A multi-call run anchors like a single call: the hop lands from `onPlan`, the brief keeps the decided anchor, and a grouping part resumes only under the anchor plan it was grouped over (`anchorPlanDigest`: the previous brief's head and index and its carry, fixed by `loadStoredParts(previous)` before any hook runs). A hook's own throw is classified before it crosses the engine: a run signal or a stamped failure passes as it is, anything else (a store or Postgres error) is `TransientJobError`, so graphile retries and the parts already paid for stay; `runGenerator` keeps a run signal's class the same way. The span's parts are deleted right after the brief write, by a run that finds the pair's brief stored, and when a permanent failure lands after every missing detail call stored its part (the merge or the write failing over the stored parts would fail the same way on every resume, so a re-trigger regenerates); those three deletes only warn when they fail, since the next run over the stored brief sweeps what is left, while the wipes of stale parts before any detail call still fail the run. Any other failure, whatever the code, keeps them for the retry or the re-trigger, and `sweep-generation-parts` bounds what neither comes back for. `logic/git-attributes.ts` reads the DEFAULT branch's `.gitattributes` (never the PR head) for the engine's generated and vendored files, three ways: content, none (absent, over its cap, or refused for good, as not text, not a blob or a permanent GitHub error: every file is read in full, and the parts digest is the empty file's) and unread (a failure a retry may clear: the engine still reads every file in full, but a run over a span holding parts, and a multi-call run over an empty one, ends transient as `github-unavailable` before any paid call, keeping every stored part for the retry, so no part is ever stored or wiped under a digest of a file the run never saw; a single call over an empty span runs). The span's parts are read before the generating phase (`loadStoredParts`), outside the engine's single-call check, which reads a hook's throw as nothing stored, so a store error ends the run transient there too. `deps.detailConcurrency` and `deps.forceMultiCall` (`generator.detailConcurrency`, `generator.forceMultiCall`) ride through to the engine; the call plan itself is the engine's.
- **Pool routing** (`logic/pool-routing.ts`) runs after the PR read and the author gate, before the claim (a gated run posts its on-demand Entry from the pool it landed in, never queueing for a large slot): a normal-pool run whose counts predict multi-call (`predictCallPlan`: more than 120 changed files, or additions plus deletions past 400k tokens at 67 bytes a line) moves its job to the large pool through persistence's `routeToLargePool` under the same job key and ends with nothing claimed, recorded or marked; when an unlocked job already waits under the key it stands down the same way. A large-pool run never moves, a wrong guess runs where it landed, and a run over the pair's stored brief stays. A recovery run routes the same way under the head's recovery key once `shouldRecoverClaim` found a claim to take over, before anything is marked.
- **A multi-call run is pinned once its first detail call starts** (`watch.pin()` in `logic/supersession-watch.ts`, from the engine's `onDetailStart`): a moved head is recorded on the watch, never thrown, the poll and the pre-call checks stop reading the head there (the tick renews the lease alone), the lease keeps renewing, the run finishes on its own head and ends `succeeded` with no `superseded` mark, and its narrative and delta cores are still written. Every Entry post of such a run reads the head fresh first and stands down on a moved one; the newer head's run owns the thread. A fresh read that finds the run's own head again (a push, then a push back) undoes the recorded move: the post goes up and the poll resumes. A url-box run schedules the observed head once it ends, succeeded or failed for good, as every supersession path does; an installation's push webhook already queued it, and a retried failure leaves it to the retry's PR read. A lost claim still ends a pinned run. A run that would write a brief and finds another head of the PR under a live claim (`readOtherHeadLeaseMs`) stands down and re-queues for one head poll later, or the lease's end if sooner: a brief written beside a pinned run would take the head index that run derived at open, and an unpinned holder ends superseded within a poll.
- **A span key's marks never certify a core computed from other bases** (`logic/span-marks.ts`). Over a key with no marks, narrative or delta stored, the revision span's marks go first, so a run stopped at the narrative (a push, the cap, a last-attempt shutdown) still leaves the span readable and a later run of the head writes the narrative. Otherwise they follow the narrative at once, unless a checkpoint shares the key and a delta is stored there: that key runs first in the delta loop and its marks follow its delta. A checkpoint's own key writes its marks after its delta. The row stores the bases the span was read against, and a stored narrative or delta is kept only under marks written from the bases resolved now; a same-head retarget or a returning head rewrites all three. Stale marks are dropped right before the first rewrite under the key (narrative, delta or either skip record), so a run that stops between that rewrite and the marks write leaves the key unmarked, never marked from other bases. A narrative that fails over marks that are not current, stale or absent, or a stored brief that cannot be read back, withholds the marks and leaves the shared delta as stored, so no row certifies text it was not computed with.
