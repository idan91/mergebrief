# Pre-claim gates

- **The author gate runs before any claim** (`logic/author-gate`): a head ingest projected `awaiting-trigger` posts the on-demand Entry under the Entry gate and ends. A bot PR with no Trigger approval goes on only when the default branch's `settings.yaml` lists its login in `trustedBots`; unlisted or unreadable, the run marks the row `awaiting-trigger` and posts the same body. The mark takes the pull request's row lock, as an approval does, and refuses a PR approved since the run read it; that run stands down and the approval's job runs the head. A head ingest held before an approval goes back to `pending` with a fresh job (`releaseApprovedHold`) instead of posting. A settings read that still fails transiently after the in-run tries retries while graphile has attempts left, the row reading `failed` as `github-unavailable` between attempts, since the hold it would otherwise write waits for a person; a refused read or the last attempt holds. A gated run takes no claim, records no attempt and reaches no model, and no failure moves an `awaiting-trigger` row, not even one thrown before the run read it (the store's unclaimed marks answer `status-kept`), so a retry meets the gate again. Url-box jobs, recovery runs, a stored brief's run and a succeeded row are never gated. The on-demand body names no head, so a later push finds it live and does not re-ping. The post re-reads the row first and leaves a head a click already moved on to the run the click queued, and it checks the head like every Entry post and, as the capped post does, stands down on an unread one. Persistence's `claimRun` refuses an `awaiting-trigger` row as well: the backstop behind this gate, never its replacement.
- **The trigger-condition check runs after the author gate, before pool routing and any claim** (`logic/condition-check`): the instance's and the default branch's `triggerConditions` merge per kind, a settings read a retry may clear is read again in the run, never through graphile (a refused read or the last try applies the instance's alone), a `paths` condition reads the PR's file list here only when it can decide the verdict (not while another plain condition is unmet, whose hold then lists no `paths` item, nor any `any` group holding one, until the others pass, nor while an `any` group with no `paths` member holds the head with every member unmet, its `bots` and `ci` members judged on the reports read before the file list, nor for an `any` group another member meets), failing as the run's own read would and handed on so the run never reads it again (a run bound for the large pool leaves it unread, so `paths` reads as met, the run routes, and the large pool's run reads the list once and decides), and matches a rename by its new or old path (the old one never reaches `buildPrMetadata`'s generation input) among the files GitHub lists, at most 3,000, so a larger PR matches on those alone, a `bots` or `ci` condition alone reads the head's check runs and statuses (plus reviews for `bots`, the base's ruleset-required checks for `ci: required`) once each, a 403 on the check-run or status read holding as the permission missing, never failing (each read carries its own flag: `clean` reads the check-run one; a ruleset check pinned to an App counts that App's latest run under the name alone, and only when it has none the latest status a bot account posted under the name, never a user's, since the status cannot tell which App's bot; any `ci` name passing, or reading nothing, while either read was refused holds as missing, unless its pinned App's run decided it, and only such a name sets `permissionMissing`, so a failed or running name shows as itself), and an unmet condition marks the row `held` with every unmet item (`markHeld`), logs `generation.hold` and ends: no claim, no attempt, no model. `reviewRequested` and `paths` stay met for the PR once met, from the PR row's stamps (persistence's `readConditionStamps`, read from the row pickup loaded): `reviewRequested` by a pending request, its stamp, or a submitted review other than a bot's or the PR's author's, on a private (not internal) repository from anyone, elsewhere from an owner, member or collaborator (`TRUSTED_AUTHOR_ASSOCIATIONS`, no permission read; the api's review webhook stamps a reviewer its permission read trusts, so this is the fallback for a review the webhook never stamped) (the review list read only when neither of the first two holds, shared with `bots`), and `paths` by a stamp under the current globs' digest (`digestPathGlobs`, sorted and deduplicated), which skips the file list read, else by a match, scanned once per run (`addPathsMatch`) and read by both the verdict and the stamp. A run writes the stamp a condition seen met by evidence owes (`deriveOwedStamps`) before it holds or claims, only where the row lacks it, and a failed write warns and the run goes on; a stamped member counts inside `any`. A hold the store refuses stands the run down. Url-box jobs, recovery runs, a stored brief's run, a succeeded row, a head a Generate click stamped and a PR generating on every push (`generate_every_push_at` set) are never checked; a hold the store refuses because the switch went on after pickup goes on to the claim, since the switch queues a job only for a head it finds held. A kind with no check in `evaluate.ts` is met. Under the Entry gate the held body (`entryComment.held.*`, third-party text as fenced inline code) edits an existing Entry comment in place, so nobody is notified again; a PR with no Entry gets one posted. It writes over any marked body but this head's closed one and is left alone when the live body already matches; a closed body it leaves queues the head's sync, which reads the PR fresh; the post re-reads the row and the head as the on-demand post does (`logic/status-entry`), and the sync rebuilds it in place from the row. Every generating post edits this head's live held or generating body into the generating one, on an unread head too and on a retry or recovery run whose row reads `failed` or `pending`, so a released hold's ready post is its one ping and a retry after the generating post landed pings no second time; any other live body is reposted as usual. The held post, the generating post on a current head, its in-place edit on an unread head and the large run's generating edit each read the head again once the write lands, since a newer head's body posted in between is gone under it: a moved head gets its own Entry sync. A failed read queues nothing, since this head's sync stands down on a moved head, so the thread keeps the body until the newer head's next Entry write.
