# Spend cap and claims

- **The daily generation cap gates ONE boundary**: `applySpendGate` claims the row through `projection.claimRun` before any provider call, so a run never counts itself. The gate sits after the GitHub read and the brief lookup: a job whose base and head pair already has a stored brief takes no claim while no claim names its row (a claim live or lapsed sends it through `claimRun`, where it answers `running` or takes the lapsed claim), counts only if it pays (its first provider call is charged under the cap lock through `chargeRun`; refused there, it logs `spend.cap.trip` and stands down without a claim), and settles a row no run holds through `settleStoredBrief` however it ends with no retry to follow: success, the cap at either check, or a failure for good. No run marks a `succeeded` row `failed` or `superseded`, not even one that throws before reading it. Such a run may still owe a checkpoint delta or a narrative, so at the cap a count-only check refuses it before any provider call. A run ingest did not project (the live base moved past the stored one) projects itself before the gate.
- `claimRun` claims the row with a run id and a lease (`CLAIM_LEASE_MS`) renewed on the head-poll tick, and queues the head's `recover-generation` job for after the lease in the claim's own transaction. Only a claim records an attempt, a graphile retry's included; a head takes at most 3 claims between triggers, and the fourth is `exhausted`: it logs `job.retries.exhausted`, and the claim itself has ended the row `failed` as `attempts-exhausted` (an earlier failure stays), or settled it when the brief is stored, with the head's Entry sync queued. The run never marks the row after a refused claim; it posts the failed or capped Entry only for the end the claim returns, and re-reads the row after the head read, standing down when a trigger moved it. A `hopeless` claim (the row failed with a Cannot-help code) stands down without a write, a post or a retry, and a condition hold over such a row is refused the same way. Every later row write is fenced by the run id, and a lost claim stands down without a write or a retry. A recovery run claims the row even over a stored brief, and its claim queues the head's next recovery job like any claim; the same key ends this job's own retries, so a takeover that fails transiently or meets a shutdown hands the row back (`awaits_recovery`) and posts nothing, and the next recovery job reruns it, the claim budget ending the chain. A recovery job runs only a lapsed claim or a handed-back row, never a row a regular run left. It marks nothing before the claim step, and a throw there fails the row like any run; once its attempts end unclaimed, it ends `failed` (`attempts-exhausted`, or a permanent failure's code) the lapsed claim it found, through `endLapsedClaim`, or the `pending` row a takeover's shutdown handed back, through `endReleasedClaim`, or keeps the failure a takeover handed back, and posts the failed Entry; a moved head ends either `superseded`. The dead holder's own job stays locked for 4 hours, and any `add_job` on its key before then detaches it with its attempts spent; the attempt budget and the stored-brief path bound what it can still pay.
- At cap the run is SKIPPED: terminal `capped` (not `failed`, no retry, no attempt consumed), written by the claim, `evt: spend.cap.trip` at warn. The Entry comment is UPDATED only if one exists and no brief is stored for the pair, never created; a row already marked `failed` keeps that status. `spend.maxGenerationsPerDay` is one number and `spend.cap.trip` still carries `repo`.
- A claimed run that succeeds with no provider call (a brief carried over an unchanged span, a takeover with nothing left to pay) gives its units back through `refundRun` before its success write (its attempt row stays at 0 units), so it costs the cap nothing; its claim still counts toward the head's 3 attempts.
- A large run claims its detail calls' units through `claimRunUnits` (persistence's `claimUnits`, under the cap lock). Refused, it ends its claim `capped` with `{needed, left, cap}` as the row's `error_params`, logs `spend.cap.trip` with them, updates the Entry as the cap does with a heading that names them, and stops through `SpendCappedSignal`. A run needing at least the whole cap fits no day, so its Entry names the cap instead of the next push.
