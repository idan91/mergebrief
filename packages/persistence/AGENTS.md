# packages/persistence: agent notes

The persistence layer for the self-host backend. The schema follows the maintainers' Postgres-schema decision record; code that diverges from it amends that record first.

Repo-wide conventions apply (root AGENTS.md); refinements below.

## Map

`src/testing/` is the PGlite cross-package test harness (`exports["./testing"]`, dev-only).

What the layout can't show:

- `schema/` is one drizzle file per table.
- `stores/ingest.ts` is the transactional webhook→upsert→enqueue boundary (a trigger with no GitHub time, such as a review, naming a head that has a row and is not current counts for the current head; naming a head with no row it keeps, since that push may have been lost, unless the review came before the current head's trigger), plus `requeueGenerateJob`, the worker's re-enqueue of a held run's job, `routeToLargePool`, which moves a running job to the large pool's task under the same key (`generate-large`, or `recover-generation-large` for a recovery run) and stands down when an unlocked job already waits there, `scheduleClaimRecovery`, which moves a head's `recover-generation` job past a live lease, `queueEntrySync`, the head's keyed `sync-entry` job (installation scope only, `ENTRY_SYNC_MAX_ATTEMPTS`), and `triggerOnDemand`, a pusher's fresh run of an open PR's current head that failed in a way a rerun can help, with no stored brief, or that awaits its trigger with an approver named (claims reset, job replaced; an awaiting-trigger head also records the Trigger approval), installation scope only.
- `stores/queue.ts` holds every `graphile_worker.add_job` call this package makes, the job payload builder, and `readQueueJob`, the one read of graphile's job table; ingest and `claimRun` (which queues the head's recovery job in the claim's transaction) both go through it.
- `stores/url-box.ts` holds `resolveUrlBoxOwner`, which answers which owner holds a pasted PR.
- `stores/webhook-delivery.ts` is the webhook delivery seen-set, keyed by the SHA-256 of the verified `X-Hub-Signature-256` header; the unsigned delivery id rides beside it for log correlation only.
- `stores/user-settings.ts` is per-user state keyed by GitHub user id, not tenant-scoped on purpose: a person spans installations. One typed column per setting.
- `stores/inbox.ts` holds the ONE multi-scope read, the Inbox list; `test/scope-containment.test.ts` refuses a second store source that spells an installation set (`inArray` over `installationId`, or a raw `in (`).
- `auth/` holds the PRE-tenant resolvers (they PRODUCE the tenant) and owns the credential rows (`auth_session`, `api_token`, `github_grant`), plus AES-256-GCM token crypto behind the key-provider interface. `createEnvKeyProvider(env)` takes the env map explicitly; the composition roots that call it read `process.env`, this package never does.
- Generated SQL under `drizzle/` is append-only.

## Invariants (enforced, don't weaken)

- **Tenancy:** callers reach the database only through this package's factories and free functions. Bound to a scope context: `createTenantRepository`, `createArtifactStore`, `createGenerationPartStore`, `createGenerationProjection`, `createIngestRoutines`, `createPurgeRoutines`, `createInboxArchiveStore`, `createLiveReadStore`. Bound to the handle alone: `createInboxStore`, `createUserSettingsStore`, `createWebhookDeliveryStore`, `createGrantAuth`, `createSessionAuth`, `createTokenAuth`. Free: `writeAudit`, `sweepAuditLog`, `sweepClosedPullRequests`, `sweepExpiredSessions`, `sweepDeadCredentials`, `sweepWebhookDeliveries`, `sweepStaleGenerationParts`, `deleteUserCredentials`, `resolveUrlBoxOwner`, `readSpendBreakdown`. The raw drizzle handle hides behind the opaque `AppDatabase` (module-private in `src/db/handle.ts`); `internal()` is the in-package unwrap and is never re-exported from `index.ts`.
  - Two scope worlds exist (`src/stores/scope.ts`): the installation tenant (`installation_id`) and the url-box owner (`pull_request.owner_user_id`, children marked by a NULL `installation_id`). Exactly one of the two is set on `pull_request`, CHECK-paired with `source`.
  - Every read filters and every write stamps through the resolved `RowScope`. Per-PR child writes verify the parent `pull_request` belongs to the scope inside the same transaction; owner-world child reads add a `pull_request` semi-join for owner isolation. Credential rows hold no installation and never sit behind a scope: they live in `auth/`, keyed by token hash, grant id or reviewer, and the credential sweeps (`sweepExpiredSessions`, `sweepDeadCredentials`) are instance-wide. Every credential transaction locks sessions, then tokens, then grants, and several grants in id order: the browser mint (`mintTokenFromSession`) takes its session `FOR SHARE` first, so a logout either waits for it or refuses it.
  - Type-level containment tests in `test/tenant.test.ts` and `test/owner-scope.test.ts` guard this. Keep them passing.
  - `matchesWorld` matches every owner's rows in the owner world, so each use relies on a parent check. `test/scope-containment.test.ts` lists every use with the check it relies on, and `test/owner-scope-reads.test.ts` calls each session method with another owner's ids. A new use joins the list; a new `ReviewSessionRepository` method fails typecheck until it has a cross-owner case.
  - Every unscoped read is named here, and a new one is argued in its PR: `resolveUrlBoxOwner` (an owner id, never a row, never an installation row), the credential reads in `auth/` by token hash, grant id or reviewer (`listForUser` lists a reviewer's token metadata), user settings by GitHub user id, the webhook delivery seen-set by signature digest (`hasRecentDelivery`: it runs before any tenant write, and a signature names no tenant row) with its instance-wide `sweepWebhookDeliveries` (every delivery past the 72-hour window, one statement), `countStartedRuns` and its free form `readSpendBreakdown` (instance-wide unit sums for the daily cap and the Operator's spend read), `sweepAuditLog` (instance-wide audit retention), `sweepStaleGenerationParts` (instance-wide: every generation part span whose newest part is over a week old, unless a live claim holds its head, one statement), `sweepExpiredSessions` (instance-wide session expiry, batched 500 per transaction), `sweepDeadCredentials` (instance-wide: a grant a dead token still holds once no session or live token uses it, by the same rule as `deleteOrphanedGrants`, then every token revoked or expired over 30 days ago, batched 500 per transaction; both sweeps hand each committed batch's orphaned grants to the caller's `OrphanedGrantSink` so the worker revokes them at GitHub even when a later batch fails), `deleteUserCredentials` (every session, token and grant of one GitHub user: the revoke webhook names a user, never a tenant; it writes one `revoke-app-authorization` audit row with the counts) and `sweepClosedPullRequests` (instance-wide pull request retention: every row closed or merged before the operator's window, both scope worlds, batched 500 per transaction with one `delete` audit entry per installation or owner each batch erased from).
  - Within that order, every table's rows lock `FOR UPDATE` in id order wherever one transaction takes several: `deleteSessionsWhere`, `retireGrant`, `deleteUserCredentials` and the sweeps. A new multi-row credential write keeps both orders, or two of them deadlock.
  - Several scopes in one call is for reads and for the Inbox list only: a viewer reaches several installations, and the list is the one read that spans them (an `IN` over installation ids plus the viewer's own url-box branch). Every write keeps one scope; a write stamp is always one installation or one owner.
- **Artifacts:** idempotent `ON CONFLICT (natural key) DO UPDATE` writes; natural keys lead with `installation_id`. `comparison_marks` and `hunk_span` bodies are coordinates-only (strict Zod; no `baselineLabel`/`baselineIndex`/line content), so neither holds code. `revision_narrative` writes verify brief anchoring.
  - `comparison_marks` carries `prev_base_sha` and `new_base_sha`, NOT NULL: the bases each head's PR diff was read against when its span was computed. Every write replaces them, and marks never certify a core computed from other bases: a writer writes the row before the key's narrative and delta only when neither is stored, else after them, so its refs certify what is stored under the same key, and `comparisonMarks.delete` drops a stale row before the key is rewritten. `revision_narrative.skipped` and `delta.skipped` stamp any skip record at write, for the comparison listing. The span read refuses a key only when its stored narrative or delta body is a span-too-large skip record, read from the body, so a narrative off by config or a delta cut at its output cap is never a refusal.
  - `brief`, `delta` and `revision_narrative` carry a NOT NULL `body_version`, and every writer stamps its body shape version; a rewrite replaces the stamp with the body.
  - `generation_part` (`stores/generation-part/`) holds a multi-call run's grouping output and finished detail calls under the brief's span (`base_sha`, `head_sha`) and a `part_key` (`GENERATION_PART_KEY_PATTERN`, CHECK-held; the store writes and reads back only brief-core's `PartKey` shapes, and a stored key off them throws `InvalidArtifactBodyError`), so a retry resumes from them. Its body is a `kind`-discriminated union (`GenerationPartBodySchema`, `GenerationPartKinds`): a `grouping` part carries brief-core's `GroupingGenerationSchema` (the grouping answer) plus the sha-256 digest of the `.gitattributes` it was read under (`gitAttributesDigest`) and the anchor plan it grouped under (`anchorPlanDigest`), a `detail` part chunks only over brief-core's `PartChunkSchema` (which accepts a repo's custom risk names by shape); no key beyond the grouping output or a detail call's attribution, so a part never holds code text. The schema is closed at the body and the chunk, and nested shapes drop unknown keys; the stored text is the parsed value, and a body off the closed levels throws `InvalidArtifactBodyError` on write and on read. `deleteForSpan` is the only reader-side removal; `sweepStaleGenerationParts` and the pull request's cascade are the others.
  - `chunk_layout` (`stores/artifact-store/chunk-layout.ts`, `createArtifactStore(...).chunkLayouts`) is the one sidecar keyed by a `brief` row (`brief_id` unique, the conflict target), holding the brief's per-chunk and per-remainder-file row counts under brief-core's closed `ChunkLayoutBodySchema`, so it never holds code text. `briefs.write` replaces it inside the brief's own transaction (a write without `chunkLayout` drops it), so a rewritten brief never keeps the previous run's counts; `chunkLayouts.backfill` backfills a brief stored without one, verifying the brief in scope and on the same PR in its transaction, and never replaces an existing row. The read joins `brief` on the span (`base_sha`, `head_sha`). A brief with no row is the reader's estimate path.
- **Migration lock:** `src/db/migration-lock.ts` is the one lock every migrator shares. `ensureAppSchema` holds it once across the app schema and the caller's `migrateQueue` step, since graphile's own install fails on a concurrent one and this package takes no `graphile-worker` dependency. Session-level on a dedicated connection, so it needs a direct or session-mode URL; a waiter blocks, warning as it goes, and gives up at `MIGRATION_LOCK_WAIT_MS`, since an api that exits fails `docker compose up` and strands `web`. A check-only boot writes nothing and takes no lock. A new migrator runs inside it.
- **Migrate command in the refusal:** `ensureAppSchema`'s check-only refusal names the manual command through `options.migrateCommand`; `resolveMigrateCommand(runtime)` picks the image form under `Runtimes.COMPOSE_WORKER` and the checkout form otherwise. The caller reads `MERGEBRIEF_RUNTIME`; this package never reads env.
- **Instance version:** `instance_version` is one row (`id` is a `true`-only boolean primary key under a CHECK). `ensureAppSchema` writes the running version there after the apply, through `src/db/instance-version.ts`; a check-only boot stays read-only and leaves the row alone. `db.version.upgrade` at `info` when the row moves forward, `db.version.ahead` at `warn` when a newer version last recorded it. A dev build (`dev`, `0.0.0`) never replaces a real version, and a prerelease (`1.5.0-rc.1`) is not a version at all: `parseSemver` refuses the `-` suffix so an RC can never compare equal to the release it precedes. It never refuses; a refusal would kill rollback by compose file.
- **Audit:** append-only, no outbound FKs: no update or delete helpers exist. The only removal is the instance-wide retention sweep in `src/stores/purge.ts` (`sweepAuditLog`), unset by default, refusing any window under the 30-day floor. Pull request retention (`sweepClosedPullRequests`, the instance config's `retention.pullRequestDays`, unset by default, one-day floor) lives beside it and reads only `pull_request.closed_at`: closing a PR arms nothing, so a row closed before the setting existed is swept like any other.
  - A row holds ids, tokens and numbers: never a body, never free text, never an address.
  - Metadata takes OPEN keys and CLOSED values (`src/stores/audit.ts`): a token, a finite number, or a boolean, nothing else. The value rules are the PII enforcement; weakening them needs a matching decision-record note.
  - `operation` and `target_type` are open token vocabularies (the descriptors belong to `apps/api`, whose choke point writes every request-path row), shape-checked in code and by a DB CHECK. Rows this package writes itself (purge sweeps, the mint transaction, the credential wipe) name their own operation token, apart from any descriptor id.
- **Carry-over:** evaluated on read, in memory, creating nothing. A read mark carries only against `brief.carried_chunk_ids` (a bare chunk-id match would mark unopened Chunks read); a hop chain that cannot be linked end to end orphans every anchor. Orphaned work is unplaced, never deleted.
  - MATERIALIZED by the first write: one transaction creates the session, copies the carried rows with their verdict columns, and applies the write. It re-reads the previous session's rows rather than trusting the read's payload, and only the session's creator copies: a concurrent first write cannot double the rows.
  - Every session write takes a row lock (`FOR UPDATE`) on its own `review_session` row, and a materialization locks the previous session's row before it creates its own. Lock order is previous, then own, on every path. A write to the previous session either commits before the copy reads it or waits and is refused as frozen; two writes to one session run one after the other, so a limit checked inside the write holds. The freeze check precedes the insert: a refused first write leaves no session row. `test/review-session-postgres.test.ts` proves the waits on real Postgres.
  - A carried draft keeps its previous row id to the payload, and each copy stores its source row, so one addressing form works on both sides of materialization. A session freezes only once the reviewer materializes a newer one, never because a newer Brief exists.
- **Spend ledger:** `generation_attempt` holds one row per claimed or paid run (`claimRun`, or `chargeRun` for a paid run over a stored brief) and is the daily cap's only counter (`countStartedRuns`, instance-wide, the sum of `units`). A row starts at 1 unit; `refundRun` sets it to 0 for a claimed run that finished without a model call, keeping the row (only lowering the count, so no lock); `claimUnits` adds more under the same instance lock and refuses past the cap with the units needed, the units left and the cap, which the run's `finishRun` stores as a `capped` row's `error_params`, and a run started before the claim's UTC day moves onto it with every unit it holds, so a claim after midnight counts against that day's cap (conservatively: that day also pays for the units the run carries); `recordPartsPlanned` stores the grouping's plan (`parts_total`, and `parts_done` starting at the parts an earlier attempt stored), `recordPartDone` counts each further part, and `readRunAttempt` reads a run's row for the PR meta's progress, its start from `recorded_at`, which nothing moves (`started_at` is the cap's day key). Rows hold ids, counts and timestamps only. No FK to `generation`: a purge never erases the day's spend.
- **Generation claim:** a `generation` row is held while `run_id` is set and `lease_expires_at > now()`. `claims` counts the claims since a trigger last projected the row; `claimRun` refuses a fourth as `exhausted` (`MAX_GENERATION_ATTEMPTS`, also every job's graphile `max_attempts`), and an `awaiting-trigger` row outright, so no run spends on a head waiting for its trigger approval. An `exhausted` or `capped` claim writes the row's end in its own transaction, under the row lock a trigger also takes, and names it (`ClaimEnds`): `settled` over the run's stored brief, `left` for a row written past its pickup or held by the previous release's run, `kept-failed`, or `marked` `failed` as `attempts-exhausted` or `capped`; with `entrySync` it queues the head's `sync-entry` in that transaction, except for a left row or a capped claim's kept failure (the sync would replace the run's capped body with the failed one). CHECKs hold the shape: a `failed` row has a code, and `run_id` and `lease_expires_at` are set together, only on a `running` row (a `running` row with no claim is the previous release's). Fenced transitions name the holder's run id; unclaimed ones write only a row no live lease holds, and the terminal marks (`markFailed`, `markSuperseded`, `markCapped`) never an `awaiting-trigger` or `succeeded` one, answering `status-kept`; `markAwaitingTrigger` and ingest's `releaseApprovedHold` take the pull request's row lock before the head, as every trigger and approval does, and read the approval under it, so the hold answers `trigger-approved` on an approved PR and the release moves only an approved PR's held head; `endLapsedClaim` writes only a row a lapsed claim still names, and `endReleasedClaim` only a `pending` row no claim names that a recovery takeover handed back (`awaits_recovery`, set by a takeover's release or retried failure and cleared by every later claim, trigger and row write; a failed row an end leaves unwritten keeps it, read by no job, since only a claim queues a recovery job and a claim clears it); each returns `claim-lost` otherwise, and so do `claimRun` and `chargeRun` on a row that is gone, since nobody holds a claim on a missing row. Every lease comparison uses the database clock, and so does freshness: every `updated_at` write stamps `clock_timestamp()` (never `now()`, the transaction's start, or a process clock), and a `pickedUpAt` fence is a `DatabaseTimestamp` from `readClock`, compared as `::timestamptz`.
- **Errors:** a call that resolves a parent row outside the caller's scope throws `ScopeViolationError` (`stores/scope.ts`, exported from the root); the api answers 404 and the worker fails the job without retry. Ingest's queue and trigger routines and the generation store's guarded transitions answer a row outside the scope as they answer a missing one instead: nothing queued, `not-found` or `claim-lost`. A marks or hunk-span body that fails its coordinates-only schema throws `InvalidArtifactBodyError` (`stores/artifact-store/index.ts`), a writer defect the worker also fails without retry. An upstream error reaches a message only sanitized: `markFailed` sanitizes any failure `detail` itself via `logging`'s `sanitizeErrorDetail`, so a caller cannot bypass it. A lost compare-and-set is a refusal, not an absence: `swapEntryComment` answers `swap-lost` with the id the row holds, and `not-found` for a row missing or outside the scope.
- **Expand and contract, every release, majors included.** Release N-1 keeps working beside release N: a schema change that drops, renames or tightens splits into an Expand step (adds, copies, widens) in one release and a Contract step (drops, rewrites, tightens) in the next release of any kind, patch included. Default shape: never rename; add the new column, read new-with-fallback-to-old for one release, drop the old one next release. A true rename that needs live writes copied gets a sync trigger in the Expand step, dropped in the Contract step; a CHECK tightening accepts both values in Expand and rewrites then tightens in Contract. Decided case by case in the PR description, never a ban. A release that must break the rule is a Breaking release and its notes say so. `pnpm check:migrations` (inside `pnpm lint`, `scripts/check-contracts.ts`) holds it grep-level, statement by statement: a migration with a `DROP` of a table, column, constraint, index, sequence, type, view, trigger, schema or function, a `RENAME`, an `ALTER COLUMN ... TYPE` or a `SET NOT NULL` must open with `-- contracts <release>` naming the release whose Expand step it finishes; the gate checks the line's shape, review checks the number. A constraint drop needs no contracts line when the file carries `-- widens <name>` and re-adds a CHECK under that name; review, not the gate, judges that the new CHECK widens. The seventeen migrations that predate the rule are grandfathered by name in `scripts/migration-contracts.ts`, held exact by the test suite, and never retro-fixed. The same promise covers the graphile job payload (`GenerateJobPayload`: add one release, remove the next) and the HTTP contract (`packages/contract`, additive within a major).
- **Before the first release there is no N-1 to keep working**: expand and contract collapse into one migration that moves the data in the same step. Its first line is `-- contracts 0.1.0`, so the gate stays green.
- **Migrations:** `drizzle-kit generate` only, never `push` (the `graphile_worker` schema is owned by graphile-worker and must not be managed by drizzle; `drizzle.config.ts` scopes to `public`). Checked-in SQL under `drizzle/` is append-only. Journal `when` values strictly increase (`check:migrations`, `scripts/journal-order.ts`): drizzle applies only entries above the ledger's newest, so a lower one is skipped for good on a database already past it.

## Conventions

- **Every CHECK is declared in its table file** with drizzle's `check()`, built by `schema/checks.ts` from the `as const` map the column is typed by, or from the shape pattern its Zod schema also parses with. `test/schema-checks.test.ts` builds a database from the schema alone and fails when its CHECKs differ from the migrated ones, so a CHECK written only in SQL, or a vocabulary value added without `pnpm generate`, is red. **Adding a value is a map change plus a generated migration**, in lockstep.
  - `api_token.scope` is typed by `AccessLevels` from `types/access-levels`, the same map the Product Operation table classifies every operation by; this package owns neither a copy nor a re-export. `audit_log.classification` narrows the same map (`read` is never audited) instead of forking it.
- **`GenerationFailureCodes` is the widest of those locksteps.** It is the DB-stored failure vocabulary (distinct from the store-internal `GenerationErrorCodes`), so a new code needs THREE changes together: the `as const` map in `packages/types/src/generations.ts`, a CHECK migration, and a `generationError.<code>` template in `packages/i18n`. `apps/web` imports the map from `types` and drops a code its bundle predates (`dropInvalidKeys`), rendering the generic failed line.
- **Column types:** a column SQL reads, filters or orders takes its native type (`text[]`, `jsonb`, an integer). A JSON document read whole is `text` through `jsonDocument` (`schema/columns.ts`) with an `IS JSON` CHECK, behind its Zod schema: artifact bodies, `repo_config`, `hunk_span.spans`. `jsonDocument` replaces NUL and lone surrogates at write, so a `::jsonb` cast reads every stored row. A new query on a value inside a document gives the value its own column, then an expression index on the cast; `jsonb` only once searching arbitrary fields is a product feature.
- **An index earns its place** by serving a per-request read on a non-key column or a sweep that deletes by a timestamp range. Every foreign key column also leads an index: a parent delete scans the child for it, and the sweeps delete parents in bulk (`test/schema.test.ts` holds this). Admin and one-off reads seq-scan: at self-host scale the write cost on append-heavy tables outweighs them.
- **Store calls are spans.** Each factory returns its methods through `traceStore` (`stores/trace-store.ts`, over `logging`'s `traceMethods`), named for the store (`reviewSessions`, `briefs`), so a trace groups a call's queries under `<store>.<method>`; a `ScopeViolationError` is the caller's answer and leaves the span unfailed. A new factory does the same.
- **Every `pull_request` update moves `row_version`** (`buildNextRowVersion`): the live read takes a stored GitHub time as its own only while the row is still at the version the read was planned against, so a writer that skips the bump lets a stale read overwrite it. `test/tenant.test.ts` and `test/live-read.test.ts` hold this for each writer.
- One scoped exception to verb-first names: Drizzle column-DSL helpers (`tenantColumns()`) stay noun-named, matching Drizzle's own `bigint()`/`text()` register.
- DB identifiers stay snake_case (Postgres convention); TS property names camelCase.

## Verification

`pnpm -C packages/persistence test` runs PGlite against the checked-in migrations. A test file shares one instance (`registerSharedPglite` in `test/helpers.ts`, reset before each test by `resetPgliteHarness` on `persistence/testing`); a test that alters the schema, replaces `add_job` or logs statements takes its own. The real-Postgres suites read `MERGEBRIEF_TEST_POSTGRES_URL` (`readTestPostgresUrl` on `persistence/testing`, which the api's `refresh-postgres.test.ts` and the worker's real-graphile test read too), never `DATABASE_URL`: unset, they skip locally and fail under `CI`. Run them against a throwaway container, never the development database: `docker run --rm -d -p 55433:5432 -e POSTGRES_PASSWORD=throwaway postgres:17-alpine`, then `MERGEBRIEF_TEST_POSTGRES_URL=postgres://postgres:throwaway@127.0.0.1:55433/postgres pnpm -C packages/persistence test`. Optional real-Postgres migration smoke: `docker compose up -d postgres`, then `DATABASE_URL=postgres://code_review:code_review@127.0.0.1:5432/code_review pnpm -C packages/persistence migrate`.
