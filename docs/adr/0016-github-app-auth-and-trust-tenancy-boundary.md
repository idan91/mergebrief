# GitHub App, Reviewer Auth, and the Trust/Tenancy Boundary

One ADR for the product's whole trust surface: the per-instance **GitHub App** (least-privilege scopes + activation), **reviewer authentication** (GitHub OAuth + a repo-access gate on every read), the **tenancy boundary** (instance = trust boundary; rows scoped by `(installation_id, repo)`), **secret handling**, the **all-inputs prompt-injection invariant**, the hosted **"no raw code" posture**, **retention/erasure**, and the **architectural boundaries** that keep SOC2 a later operational program rather than a redesign. Closes epic gating decisions #3 (App scopes) + #4 (secret storage) and the deferred GPT-5.5 review item #6 (trust posture). Sits under the OSS-self-host-first model (ADR 0017, `docs/system-overview.md`).

## Context

The product handles orgs' private source code; the GPT-5.5 review named trust/tenancy the largest gap and "a sales blocker earlier than expected." Distribution is OSS self-host first (ADR 0017): the **adopter is the data controller**, which removes most of our obligations now — but the boundary must be designed so a future hosted, multi-tenant mode is an operational lift, not a re-architecture. Runtime flow is in `docs/system-overview.md` §3.

## Considered Options

- **Activation surface.** Check Run (tidy, but the CTA is a buried "Details" link) · **PR comment (chosen)** — visible CTA, matches CONTEXT.md's Activation; Check Run deferred.
- **Comment lifecycle.** Edit-in-place (no notification, gets buried) · **delete + repost (chosen)** — stays at the bottom and fires a "re-review ready" notification; debounced to one per settled head.
- **Comment permission.** `Issues: write` · **`Pull requests: write` (chosen)** — already required for the reviewer's review, and it also authorizes the PR-conversation comment, so `Issues` is dropped.
- **Persisting code (hosted).** Persist diffs · **fetch on-demand by token (chosen)** — persist only the analysis; baseline snapshot configurable.
- **Secret redaction.** None · broad DLP (rejected — degrades analysis) · **high-confidence patterns, line-preserving (chosen)**.
- **Tenancy.** Instance-only · **scope every row by `(installation_id, repo)` from day one (chosen)** even while single-tenant.

## Decision

1. **Per-instance GitHub App.** Identity (app-id, private key, webhook secret, OAuth client) is all env/config; created via the app-manifest flow; logo uploaded per instance. No hosted-singleton assumption — self-host and hosted differ only in deployment + tenancy density.
2. **Least-privilege scopes:** `Contents: read` (read diffs — never write code), `Pull requests: write`, `Metadata: read`. The PR-conversation comment uses `pull_requests:write` (also needed for the reviewer's review) — **no `Issues` permission**. Events: `pull_request`, `pull_request_review`, `installation`, `installation_repositories`.
3. **Activation = one branded comment, delete + repost per debounced generation** (bottom-of-thread + a "re-review ready" notification; one ping per settled head, never per push). The Brief is read in the web app, **never posted into the PR**. Check Run deferred.
4. **Reviewer auth = GitHub OAuth (user-to-server) + session.** The reviewer's token authors *their own* review at submit; it is short-lived, **field-level envelope-encrypted at rest**, and deleted on expiry/logout. **Amended (2026-07-06, BRIEF-19 grill):** a session binds exactly ONE installation, but the binding is now user-steerable instead of "first accessible": login binds the reviewer's **default installation** (`user_settings.default_installation_id`, ADR 0018 D14) when it is still in their live accessible set (`GET /user/installations`), else the first accessible one; `POST /auth/installation` switches the live session's installation after re-validating the target against that same GitHub-derived set (never a caller-asserted id), audit-logged, with an opt-in `setDefault`. The tenant still derives from GitHub, never from caller input. **Amended (2026-07-09, BRIEF-17 grill):** first-class **API tokens** join as a SECOND PRESENTATION CHANNEL over the same session machinery — for the CLI and agents (ADR 0028), not a new auth model. An opaque `mergebrief_...` token (secret-scanner-friendly prefix) is sent as `Authorization: Bearer`; the server stores its SHA-256 hash only, and the hash resolves to a row wrapping the same envelope-encrypted GitHub token + refresh token the session row wraps — then expiry check → tenant ctx → the normal GitHub authz gate, identical code path local and deployed. Miss/expired → 401 with no hint (sessionLayer posture). A token binds exactly ONE installation chosen at mint — the tenancy invariant (#4, #6) is untouched; multi-installation is a client-side concern (named CLI profiles). Minting is browser-side only: a cookie-authed settings page (`POST /auth/tokens`), token shown once, named + listable + revocable, `last_used_at` tracked; default 90-day expiry, no-expiry allowed (self-host CI is the adopter's call), hard-bounded regardless by the wrapped GitHub refresh token dying ~6 months idle. Bearer is accepted on `/api/*` only and `/auth/*` stays browser-only, so ONE IdP path-exemption rule (`/api/*`) covers webhooks + CLI traffic forever; no per-IdP integration. Cookie reuse and GitHub-PAT pass-through were rejected (browser-shaped expiry / no installation binding, no MergeBrief-side revocation); no device flow in v1 (revisit: human onboarding friction once peers use it). **Amended (2026-07-23, BRIEF-40 grill):** the copied-pair model is retired — session and API-token rows no longer each wrap a GitHub credential pair; both reference a first-class **grant** row (`github_grant`, ADR 0018 D15) holding the ONE envelope-encrypted pair per GitHub authorization. Mint links the session's grant instead of copying ciphertext; refresh stays a serialized single-row CAS, re-anchored to the grant row. This makes the BRIEF-40 divergence (single-use refresh token copied into two rows; whichever channel refreshes first strands the other) unrepresentable by construction. Channel postures are unchanged: cookie refresh-failure still deletes the session; a dead API token keeps 401ing until its owner revokes; a grant is deleted with its last referent, in the same transaction. Rejected for the fix: **own-grant-per-token via device flow** (GitHub docs are silent on whether a second user-to-server authorization coexists with the first; the App manifest cannot enable device flow, so every self-host App needs a manual settings checkbox; the `github_app_authorization` revocation webhook does not identify which grant died and no API lists a user's tokens — research: `docs/dev/brief-40-github-token-grant-research.md`) — device flow stays parked as the onboarding revisit above, not the divergence fix. Also rejected: **copy-plus-cross-patch** (grant-family id + fan-out patching every row sharing a pair) — hot-path multi-row choreography where one missed row silently reintroduces the bug. GitHub-side revocation hygiene (inbound `github_app_authorization` handling, outbound per-token DELETE on logout/revoke) is a deliberate follow-up ticket, not this change.
5. **Authorization gate on every artifact read** — a single enforced middleware verifies the viewer has GitHub access to the repo (briefs = private source); not per-endpoint. Returns 401 / 403 / 404. **Amended (2026-07-06, BRIEF-19 grill):** three refinements, one posture. (a) **Positive-only authz cache, 60s TTL** — reintroduced (a 5-min variant was removed 2026-07-05 in favor of recheck-every-read) because the FE's generation-status polling and SSR multi-artifact loads make a GitHub round-trip per read untenable (~720 calls/hr per waiting viewer); keyed `(sessionHash, repoId)`, negatives never cached, so a revoked grant is honored in ≤60s while GitHub's own token enforcement stays live underneath. (b) **Cross-repo list endpoint** — a list cannot reuse the per-repo check; its authorized repo set comes from `GET /user/installations/{installation_id}/repositories` with the VIEWER's token (the exact installation∩user-access intersection, numeric ids, rename-proof), cached per session under the same 60s constant; a GitHub failure fails the list, never degrades to a DB-only (leaky) listing. The gate splits into a session-resolution layer (shared) and a repo-authorization layer (per-repo or installation-set) — still one enforcement point, two compositions. (c) **SSR is not a second path** — web loaders reach the read API by in-process dispatch of the same Hono app with the viewer's cookie forwarded, so server-rendered reads traverse the identical middleware; SSR'd documents carry `cache-control: no-store` (private HTML must never be proxy-cached). **Amended (2026-07-21, BRIEF-51 / [ADR 0034](./0034-observability-v1-logging-health.md)):** two deliberately UNAUTHENTICATED top-level endpoints exist outside this gate — `/healthz` (static liveness) and `/readyz` (readiness: app composition + `SELECT 1`) — answered in the server entry before the Hono app, returning constant tiny JSON that leaks no version, dependency, or tenant detail. They are infrastructure probes, not artifact reads; the gate's scope is unchanged. `/api/version` remains an authenticated CLI probe (ADR 0029 #8) and is NOT orchestrator health.
6. **Tenancy = instance is the trust boundary** (no cross-instance data); within an instance **every row is scoped by `(installation_id, repo)`** with a mandatory tenant filter — carried from day one though M1 self-host is single-tenant, so a future hosted multi-tenant mode is not a schema rewrite.
7. **Secrets.** All static secrets (model/BYOK key by env-name per ADR 0013, App private key, webhook secret, OAuth secret) live in env/secret-manager — **never in the DB, never in the repo**. The one dynamic secret (the reviewer token) is envelope-encrypted with a key resolved via a **provider interface** (env now, KMS-droppable later). Generation origin (ADR 0013) is recorded on every artifact.
8. **Prompt-injection invariant — ALL model inputs are untrusted:** PR title/description, the diff/code (including code comments and string literals), review comments, and fetched context. They are **fenced as data, never instructions**; the system prompt (the taxonomy) is the *sole* instruction authority. Containment: the **structured-output floor** (ADR 0013) limits escape into free-form output; **no-verdict + human-in-loop** bound the blast radius (worst case = a misleading-but-valid brief, still human-reviewed, never an auto-gate); rendered output is flagged untrusted to the headless consumer (ADR 0014). **Amended (2026-09-26):** raw HTML in model output renders as text and is never parsed; `rehype-sanitize` guards only text written on GitHub (comments, the PR description), which the web renderer parses on an explicit opt-in. Extends ADR 0011/0014 fencing to *all* inputs.
9. **Secret redaction before the model** — a **line-preserving** pass over the diff redacting **high-confidence credential patterns only** (private keys, recognizable key/token formats); default-on, documented best-effort. Not a general DLP (a redacted credential never changes the brief; broad redaction would degrade analysis).
10. **Hosted "no raw code" posture** — diffs are fetched **on-demand by token** at render (ADR 0006 #9), never persisted (an ephemeral per-session cache is fine; disk/DB is not). Only the **brief (analysis)** and an optional, **configurable baseline snapshot** are stored; with the snapshot off, a delta degrades to a full Brief when the checkpoint commit is GC'd. All model egress flows through the single **Generator port** (ADR 0013) — one auditable confidentiality + sub-processor boundary.
11. **Retention + erasure** — configurable retention window; sweep on PR-close + grace (ADR 0015); **purge by org/installation** (cascading, verifiable) for offboarding + right-to-erasure, with the deletion itself audit-logged.
12. **SOC2 architectural readiness — boundaries now, program later.** Design in: tenant isolation (#6), the single auth/authz gate (#5), the single code→model egress (#10), an **append-only audit log** (one emit per boundary — auth, view, generate, delete, config — immutable, tenant-scoped), the encryption-key provider interface (#7), no-raw-code minimization (#10), and cascade-by-tenant erasure (#11). Processing Integrity is already served by content-addressed idempotent writes (ADR 0006/0008) + origin tracking (0013) + the immutable Receipt (0002). The SOC2 **program** (monitoring, incident response, change management, vendor risk, the audit engagement) is operational and deferred to the hosted offering — on self-host it is the adopter's responsibility.

**Amended (2026-08-17, BRIEF-197 → [ADR 0040](./0040-review-session-server-store.md)) — two items.** *#4:* an API token now carries a **scope** chosen at mint and immutable for its life — `read` / `private-write` / `external-write`, cumulative, the same vocabulary as the Product Operation write classification, enforced inside `productRouter.action()` (a query is `read`, the ladder's bottom rung, so every scope reaches it) and refused with `scope-exceeded` (403). A cookie has no row to hold a scope, so the browser stays unlimited: the person is at the keyboard. Existing tokens backfill to full, because read-only would 403 every running CLI on deploy day. The server never learns that an agent is involved — a limit can only ever be a property of a credential, never of a session or a client's claim about itself. *#12:* the audit boundary keeps its emit interface but changes vocabulary and coverage — the descriptor `operation` id replaces the eight-value `action`, coverage is every action plus denials (never a read) from one router choke point, and "never purged" becomes a configurable retention policy whose numeric-only rule now rests on self-host backup grounds (see [ADR 0018](./0018-m1-postgres-schema.md) D9 as amended).

**Amended (2026-09-21, BRIEF-210 → [ADR 0043](./0043-no-credential-holds-a-current-installation.md)) — #4:** no credential binds an installation any more. A session names its reviewer only, a token binds none at mint, `POST /auth/installation` and `user_settings.default_installation_id` are gone, and every request resolves the installation from its repository against the viewer's live GitHub access. The "exactly ONE installation" sentences in the 2026-07-06 and 2026-07-09 amendments above are superseded.

## Why This Way

Self-host makes the adopter the controller, which removes most obligations now; the discipline is to design the *boundaries* — tenant scope, one auth gate, one egress chokepoint, an audit boundary, key-provider indirection — so the hosted offering is an operational lift rather than a re-architecture. Least-privilege, the no-raw-code posture, and the all-inputs injection invariant directly answer the GPT-5.5 trust gap; and the no-verdict / human-in-loop design that *defines* the product also caps injection blast radius — the honesty stance is a security control.

## Consequences

- The App is never a hosted singleton: every instance carries its own identity/config.
- `installation_id` on every row from day one — minor cost, large future saving (the one true redesign-avoider).
- Net-new but small: an append-only audit table, a central auth middleware, and a key-provider interface. Populating/hardening them is the hosted lift.
- The Generator port (ADR 0013) is now also the confidentiality + sub-processor boundary.
- Builds on ADR 0006 (diffs on-demand, baseline snapshot), 0008 (artifacts/anchoring/retention), 0011/0014 (fencing), 0013 (Generator port, origin, secrets), 0015 (runtime/store, deletion boundary), 0017 (distribution); closes epic gating #3/#4 and GPT-5.5 review #6.
