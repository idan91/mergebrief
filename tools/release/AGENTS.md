# tools/release: agent notes

The release tool behind `release.yml`: reads the per-release notes files, refuses a tag without one, stamps the tag's version into the shipped manifests, writes the Release body and `version.json` the workflow uploads, and exports the public snapshot of a commit on `main` as one release commit and tag on the public repository. `pnpm check:releases` is its gate inside `pnpm lint`; the other commands run on the workflow's checkout only.

Repo-wide conventions apply (root AGENTS.md); refinements below.

## Invariants (enforced, don't weaken)

- **One notes file per release**, `docs/releases/<X.Y.Z>.md` or `<X.Y.Z-rc.N>.md`, version in the filename only. Front matter is exactly three `key: value` lines between `---` fences: `date` (ISO `YYYY-MM-DD`, the tag day), `breaking`, `security` (`true` or `false`). No quotes, no nesting, no indentation, no repeated or other key; the parser is the schema beside it, not a yaml library. A `breaking` file carries an `## Upgrade` heading. Any other file in the directory is a refusal.
- **Every argument is known.** An unknown flag, a `--flag=value` form, a flag without its value or a stray positional is a usage error (exit 2), never a silent fallback to the no-tag path.
- **A tag needs its file.** `check --tag vX.Y.Z` refuses when the file is missing or any file is malformed, so the gate on the PR is the same gate the tag runs. `--json` prints `{ version, channel, isHighestStable, isHighest }` for the workflow; `isHighestStable` decides `--latest` on the Release, `latest` on npm and ghcr and whether `version.json` is written, never GitHub's own ordering; `isHighest` (over every channel) decides whether an rc takes the npm `next` dist-tag, so an older candidate published later never moves `next` back. The workflow passes the tags already published as `--known-tags v0.1.0,v0.2.0`, and placement reads those tags plus the tag itself, never the notes files: a stable file merged before its candidate ships leaves the candidate on `next`, and a hotfix tagged after a newer release is placed against what shipped.
- **The stamp edits a clean checkout once; the prune shapes the tarball after the build.** `stamp <version>` refuses a manifest whose version is not the `0.0.0` sentinel, writes the version and keeps every other key, swaps every `image: ghcr.io/idan91/mergebrief:dev` line in `docker-compose.yml` (and refuses a file with none), and touches nothing else. `docker-compose.external-db.yml` is an overlay on that file and names no image, so the stamp leaves it alone; `test/compose-files.test.ts` holds that. `prune-manifest` refuses a manifest still on the sentinel and drops `private` and `dependencies` (the bundle inlines them; the repo keeps them listed so `pnpm audit --prod` still sees them, and a published `workspace:` range would resolve to a public package of the same name). The prune runs after the last pnpm script in `apps/cli`: pnpm reinstalls before a script whose manifest no longer matches the lockfile, which prunes the bundle's inputs and fails the build. Compose files are edited line by line so comments survive; the manifest is re-serialised with two-space indent, which is what prettier writes. Nothing here commits.
- **`version.json` and the Release body come from the notes files, never by hand.** `version-json <tag> --known-tags ... --out <file>` writes `{ latest, releaseNotesUrl, releases[] }` over the stable files up to the tag, newest first, and refuses unless the tag is the highest stable release among the published tags, so the file is only ever written for the release that `releases/latest/download` will serve; candidates are left out, and an rc or an older hotfix gets no version.json. `release-body <tag> --out <file>` writes the Release body: for a stable tag the upgrade chain from `docs/self-host/operations.md` with the tag filled in (a test holds the two in step), a lead line for a breaking or security release, the backup and upgrade-step links, then the notes body verbatim; for an rc a not-for-production note with the `next` dist-tag, no chain. Every link is the Release page or the tag-pinned doc.
- **The export reads git, never the checkout.** `export --version X.Y.Z --source <ref> [--dry-run [--expect-commit <sha>] | --emit <dir>] [--out <dir>] [--public-remote <url>] [--private-remote <url>] [--authenticated-reads]`, reached as `pnpm release:export` from the root, fetches the remote `main` first and refuses a source it does not hold, lists the commit's tracked paths and writes the shipped ones with `git archive` into an absent or empty `--out` (a fresh temp dir when absent), so an untracked or uncommitted file can never ship. A relative `--out` resolves against the shell the root script ran in. A publish and `--dry-run` run every gate, then build the release commit and print the plan (source, parent, commit, tag, add/edit/delete counts, the pushes owed); `--dry-run` stops there and leaves the tree, a publish pushes. `--public-remote <url>` points a rehearsal at a scratch remote; a release never passes it. `--private-remote <url>` reads main and the records from `<url>` instead of `origin`; `publish.yml`'s plan and gates jobs pass their own credential-free clone. The version is the explicit `--version`, never computed from tags. Git enters through `GitPort` (`src/logic/git-port.ts`), the one file that spawns `git`, so the plan is tested against a fake and the port against a temp repository.
- **One manifest says what is private.** `src/logic/export/paths.ts`: `include` names every top-level entry (a dir with its `/`), `exclude` holds path prefixes, no globs, applied unconditionally; a prefix with nothing tracked under it passes. A top-level entry in neither list refuses the export (`unclassified top-level path: notes/`); classify it there, never around it. The link check reads the same manifest: a shipped `.md` that links into an exclude prefix, or writes one out at a path boundary, fails with `file:line`, except the lines `EXCLUSION_RULE_SITES` names because they state the rule. Non-markdown config is not scanned.
- **Every gate runs on the tree, in order; the first failure stops the run.** `paths` (the link check), `gitleaks` (the image `GITLEAKS_IMAGE` pins by digest, the tree mounted read-only, archives opened one level deep as CI's diff scan does, findings redacted; a file gitleaks cannot read only logs an `ERR` line and exits 0, so the gate captures its stderr through `runCapturingStderr` and fails on any `ERR` line; Docker is required; the tree's own `.github/gitleaks.toml` is the allowlist when it ships one, the same file CI's diff scan reads, and every workflow that runs gitleaks pins the same image, which a test holds), `notes` (`checkReleases` for `v<version>` over the tree's notes files and a read of the public repo's tags, which places nothing because `release.yml` places the tag; a repo that does not answer is no releases in a dry run and a refusal in a publish, under `--expect-commit` or under `--authenticated-reads`), `build` (`pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm -r typecheck`, `pnpm -C tools/categorizer test`). The build runs in a temp copy of the tree committed as a one-commit repository, with `MERGEBRIEF_BASELINE_BASE=HEAD`, because `check:baselines` needs a merge base; the copy is deleted after, so `--out` never holds build output. Tools spawn through `CommandRunner` (`src/logic/command-runner.ts`), so the gates are tested against a fake; one test runs the real scanner and skips without Docker. Each verdict prints as `gate <name>: ok|FAILED, ...` on stdout as it lands; the tools' own output goes to stderr.
- **The release commit is a function of git alone.** Its tree is built from the object db over the shipped paths (a temp index, `write-tree`), never from `--out`, and refused unless it hashes identically to the materialized tree, mode and symlink included, so what the gates checked is what ships. Author and committer are `RELEASE_IDENTITY`, both dates the source commit's committer date, the message `Release X.Y.Z`; the parent is the previous release commit (the highest-version `public/v*` record), none for the first release, so deletions fall out of the tree and nothing is merged. The body credits the `Co-authored-by:` trailers of the private commits since the previous record's source (all history for the first release), one line per address with its first spelling kept, sorted by code unit so no host's collation moves the SHA, `CO_AUTHOR_DROP_EMAILS` (the maintainer's noreply address and the agents') left out. The `vX.Y.Z` tag is annotated with the same identity and date, and its message is the `Release X.Y.Z` line alone, without the credits; `formatReleaseMessage` builds both. Same inputs give the same SHA, so a rerun rebuilds the commit it already pushed. Every object is written to a temp store layered over the repository's through alternates and discarded at exit; pushes send object SHAs, so no local branch, tag or loose object ever appears and a dry run writes nothing.
- **`public/vX.Y.Z` on the source records the mapping, written last.** An annotated private tag whose message is `public-commit <sha>`, pushed to `origin` only after the public commit and the `vX.Y.Z` tag landed, so a record means the release is public. A record on the same source resumes: whatever the public remote lacks is pushed, nothing twice. Before any push, an export refuses a version not above the last one exported and a source that does not contain the last one's source, so record order is version order and no date is read. A record on another source refuses (`0.1.0 already exported from 4e1a9c2; refusing 7b20f11`), a rebuilt SHA that differs from the recorded one refuses, a public tag at another commit refuses (`tag v0.1.0 exists at 7b20f11; tags never move`). Every push is plain, never forced.
- **Public `main` holds release commits only.** After the gates, the export fetches public `main` and, before any push, refuses unless it is the last release commit (the highest-version record's public SHA) or already the commit being rebuilt, which is a resumed run. A drifted `main` refuses with `public main at f00d123 is not the last release commit a91c456; reconcile first`, a missing one with `public main is missing; the last release commit is a91c456; reconcile first`, and a `main` with no record at all with `public main at f00d123 is not a release commit; reconcile first`. It never force-pushes; reconciling is by hand. A contribution lands in the private repository with a `Co-authored-by:` trailer and ships in the next release.
- **What ships is planned where no gate runs, and gated where nothing ships.** `--emit <dir>` runs no gate and pushes nothing (never with `--dry-run`): into an absent or empty dir, checked first, it plans as a publish does (a public repo that does not answer refuses) and writes `release.bundle` (`refs/heads/main` at the release commit, `refs/tags/vX.Y.Z` and `refs/tags/public/vX.Y.Z` at their tag objects; the release history is complete, the private history left out, so it unbundles in a full clone of main) and `plan.json` (`publicUrl`, the repository it read, then `version`, `source`, `commit`, `tree`, `tag`, `tagObject`, `record`, `recordObject`, `actions`). `--dry-run --expect-commit <sha>` runs every gate, plans as a publish does, and refuses (`rebuilt <sha>, not the planned <sha>; the gates checked another commit`) unless the rebuild is that commit. `publish.yml` runs them as three jobs, each checking the tool out at `main` without credentials: `plan` installs the tool with `--ignore-scripts`, emits and publishes the SHAs as job outputs; `gates` reruns with `--expect-commit`; `publish`, in the `publish` environment, refuses a bundle whose refs or objects are not exactly the plan job's outputs, then mints the App token and pushes only the listed actions with plain git, commit then tag, then the record with the job's `GITHUB_TOKEN`.
- **The token reaches the public repository's git children only.** `MERGEBRIEF_PUBLISH_TOKEN` is read in `main.ts` only, required without `--dry-run` or with `--authenticated-reads`, and reaches git for `pushPublic` and, under `--authenticated-reads` only, for the two reads of the public repository, each time through a credential helper that reads it from that child's environment; a remote flag whose URL carries userinfo is a usage error before any git call, `GitCommandError` strips URL userinfo from its argv and stderr, and `main.ts` routes stdout, stderr and any crash report through `redactStreamOutput`, so no usage error, refusal or stack trace carries a credential, and the public repo is read anonymously by default. `--authenticated-reads` is the opt-in for a target that is still private: `resolveExportTokens` (`src/logic/export/tokens.ts`) decides where the token goes, `resolvePublicRepositoryAccess` (`src/logic/export/public-repository.ts`) turns that one value into both the repository's `authenticatesReads` mark and the token `main.ts` hands to `createGitPort` as `publicReadToken`, and the two reads of that repository, `listPublicTags` and `fetchPublic`, run their `ls-remote` and `fetch` through the same helper; it refuses without the token, in a dry run and an emit too, without the flag a token in the environment changes no read, and with it every run, a plain dry run included, refuses a repository that does not answer (`public repo <slug> not found; MERGEBRIEF_PUBLISH_TOKEN cannot read it, or it does not exist`), because GitHub answers a token without access as it answers a missing repository. Every other git call takes an explicit env, and every git and gate child starts from the parent's env with credential-shaped names removed (`stripCredentialVariables`: any name containing `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD` or `CREDENTIAL`, a `KEY` segment, or git's `GIT_CONFIG_*` environment config as one group), held in `GitPort` and `CommandRunner`, never left to the caller. A local publish, or a local dry run or emit under `--authenticated-reads`, still holds the token in its own process for the whole run; `publish.yml` is the path where gate code runs with no credential to find, so it never passes the flag: its gates job reads the public repository in the process that spawns the build.
- **Own version grammar.** `X.Y.Z` or `X.Y.Z-rc.N`, no leading zeros, optional `v`. Narrower on purpose than persistence's `parseSemver`, which drops any suffix; a candidate sorts before its release here.
- **`licenses` gates the shipped graph, weekly.** `pnpm -C tools/release run licenses` (`run`: pnpm's own `licenses` command shadows the script) classifies `pnpm licenses list --json --prod` against the pass list in `src/logic/licenses/consts.ts`; SPDX `OR` passes on any allowed branch, `AND` needs every branch, anything unresolved fails. A package off the list passes only as a named exception with its reason, and the exception lapses when its license changes. `audit.yml` runs it on the schedule and on dispatch, never per PR; pnpm enters through `src/logic/licenses/pnpm-port.ts`.
- **The image's third-party notices follow the lockfile.** `notices` rewrites `docker/third-party-notices/` for the one `@img/sharp-libvips-*` version the lockfile holds, from that release's tag on GitHub: `THIRD-PARTY-NOTICES.md` verbatim, and `SOURCES.md` from the downloads `build/posix.sh` makes with `versions.properties` filled in, patches included, plus the SPDX licence texts at `SPDX_LICENSE_DATA_TAG`. The script is read, never run; a URL whose shell it cannot expand refuses. When the lockfile holds `elkjs`, the notices gain its line, `SOURCES.md` its section with the `kieler/elkjs` tag archive, and the folder the EPL-2.0 text. `check` refuses while a version `SOURCES.md` records differs from the lockfile's, or one side holds elkjs and the other does not, so a bump fails `check:releases` until the folder is regenerated. A licence exception whose name ends in `*` matches by prefix, which is how `@img/sharp-libvips-*` covers every platform build.
- **`src/main.ts` is the only composition root**: argv, the repo root (resolved from the file's location) and the environment the git port and the command runner start from enter there.

## Verification

```sh
pnpm -C tools/release test          # temp trees, one per refusal
pnpm check:releases                 # the gate over docs/releases
pnpm release:export --version 0.1.0 --source origin/main --dry-run --out /tmp/export   # the public tree, every gate, the commit a publish would push
pnpm release:export --version 0.1.0 --source origin/main --emit /tmp/release   # no gate: release.bundle and plan.json, as publish.yml's plan job writes them
MERGEBRIEF_PUBLISH_TOKEN="$(gh auth token)" pnpm release:export --version 0.1.0 --source <sha>   # the release itself, from the SHA resolved once and kept for retries; Idan runs it
MERGEBRIEF_PUBLISH_TOKEN="$(gh auth token)" pnpm release:export --version 0.1.0 --source <sha> --authenticated-reads   # the same while the public repository is still private; add --dry-run to rehearse
pnpm -C tools/release version-json v0.1.0 --out /tmp/version.json && pnpm -C tools/release release-body v0.1.0 --out /tmp/body.md
pnpm -C tools/release stamp 0.1.0 && pnpm -C apps/cli build && pnpm -C tools/release prune-manifest && git diff --stat && git checkout -- apps/cli/package.json docker-compose.yml
```
